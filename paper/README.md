# paper — งานวิจัยที่ใช้อ้างอิง

โฟลเดอร์นี้เกิดขึ้นเพราะคำถามของอาจารย์ที่ปรึกษาเมื่อ 2026-10-02 ว่า
**"วิธีการที่ทำมาจะรู้ได้ยังไงว่าถูกต้อง"**

ที่ผ่านมาทุกข้อสรุปในโปรเจกต์ถูกตรวจสอบ**จากข้อมูลของเราเอง** ซึ่งจับความผิดพลาด
ได้จริงหลายจุด แต่มันตอบได้แค่ว่า "จริงในข้อมูลชุดนี้" ไม่ได้ตอบว่า
"นี่คือวิธีที่วงการเขาทำกัน" วิธีหนึ่งอาจสอดคล้องกันเองดีทุกอย่าง
แต่ยังเป็นวิธีที่แปลก ล้าสมัย หรือข้ามขั้นตอนมาตรฐานที่คนอื่นเขาทำกันก็ได้

**หลักฐานต้องมีสองขา** ขาแรกคือวัดเองกับข้อมูล ขาที่สองคืองานที่ตีพิมพ์แล้ว
ตอนนี้เรามีแค่ขาเดียว

---

## วิธีใช้โฟลเดอร์นี้

```
paper/
├── README.md          ไฟล์นี้ — รายการคำถามและดัชนีงานวิจัย
├── *.pdf              ไฟล์งานวิจัย (ไม่ขึ้น git เพราะติดลิขสิทธิ์)
└── notes/             บันทึกสรุปของแต่ละฉบับ (ขึ้น git)
```

1. เอาไฟล์ PDF มาวางใน `paper/`
2. บอกให้ Claude อ่านและสรุป
3. ได้บันทึกสรุปใน `paper/notes/` หนึ่งไฟล์ต่อหนึ่งงานวิจัย
4. อัปเดตตารางดัชนีท้ายไฟล์นี้

**PDF ไม่ขึ้น git** ตั้งไว้ใน `.gitignore` แล้ว เพราะไฟล์งานวิจัยมีลิขสิทธิ์
และไฟล์ใหญ่ ส่วนบันทึกสรุปที่เราเขียนเองขึ้น git ตามปกติ

## รูปแบบของบันทึกสรุป

ทุกฉบับสรุปตามหัวข้อเดียวกัน เพื่อให้เทียบกันได้

| หัวข้อ | เนื้อหา |
|---|---|
| **บรรณานุกรม** | ผู้แต่ง ปี ชื่อเรื่อง วารสารหรืองานประชุม DOI |
| **เขาทำอะไร** | โจทย์และขอบเขต สรุปใน 3–5 ประโยค |
| **ข้อมูลที่ใช้** | ชุดข้อมูลอะไร กี่ไฟล์ เครื่องจักรแบบไหน |
| **วิธีการ** | สกัด feature อย่างไร ใช้โมเดลอะไร **แบ่ง train/test ยังไง** |
| **ผลที่ได้** | ตัวเลขที่เขารายงาน พร้อมเงื่อนไข |
| 🚩 **เทียบกับของเรา** | **สนับสนุน / ขัดแย้ง / ไม่เกี่ยว** ข้อไหนของเราบ้าง |
| **สิ่งที่ควรเอามาใช้** | ทำอะไรต่อได้บ้างจากงานนี้ |
| **จุดอ่อนของงานนี้** | อ่านอย่างมีวิจารณญาณ ไม่ใช่เชื่อทุกอย่าง |
| **คำค้นต่อ** | ศัพท์เฉพาะที่เจอ ใช้ค้นงานถัดไป |

**หัวข้อที่สำคัญที่สุดคือ "เทียบกับของเรา"** ถ้าอ่านแล้วสรุปได้แค่ว่างานนี้
เกี่ยวกับอะไร แปลว่ายังไม่ได้ประโยชน์ ต้องตอบให้ได้ว่ามันทำให้เราต้องเปลี่ยนอะไร
หรือยืนยันว่าอะไรที่เราทำถูกแล้ว

## 🚩 คำถามที่ต้องการงานวิจัยมาตอบ

เรียงตามความสำคัญ ข้อที่อยู่บนสุดคือข้อที่ถ้าตอบไม่ได้จะกระทบงานมากที่สุด

### 1. ความเร็วรอบที่เปลี่ยนไป ทำให้ค่าตัวชี้วัดเปลี่ยน — วงการแก้ยังไง

**ปัญหาที่เราเจอเอง** ตัวชี้วัดความแรงบนช่อง `o_axial` กระโดด **4 เท่าเมื่อความเร็วรอบ
ข้ามเส้น 50 Hz** โดยที่ความเสียหายไม่ได้เปลี่ยน และพบพฤติกรรมเดียวกันใน 5 คลาส

**เราแก้แบบบ้านๆ** คือจำกัดช่วงความเร็วที่ใช้วิเคราะห์ และส่งความเร็วรอบไปพร้อม
ตัวชี้วัดเสมอ

**ที่ต้องไปหา** วงการมีวิธีมาตรฐานชื่อ **order tracking** หรือ **angular resampling**
คือสุ่มสัญญาณใหม่ตามมุมของเพลาแทนตามเวลา ทำให้ความถี่ความเสียหายอยู่ตำแหน่งเดิม
ไม่ว่าความเร็วจะเปลี่ยนแค่ไหน **ต้องหางานวิจัยยืนยันว่าเป็นมาตรฐานจริง และดูว่า
เขาทำยังไง** ถ้าใช่ นี่คือตัวอย่างชัดที่สุดว่าทำไมอาจารย์ถึงถูก เพราะเราเสียเวลา
ไปกับปัญหาที่วงการแก้ไว้นานแล้ว

### 2. การแบ่ง train/test ของข้อมูลสั่นสะเทือน มาตรฐานคืออะไร

เราวัดเองได้ว่าวิธีแบ่งทำให้ accuracy ต่างกัน **27 จุด** (0.996 / 0.843 / 0.726)
และสรุปว่าต้องแบ่งตามไฟล์หรือตามเงื่อนไข

**ที่ต้องไปหา**
- งานที่ใช้ MAFAULDA รายงาน accuracy เท่าไร และ**แบ่งข้อมูลยังไง**
- ถ้าเจองานที่รายงาน 99% ด้วยการสุ่มหน้าต่าง → ยืนยันว่าข้อสังเกตของเราถูก
  และกลายเป็นจุดแข็งของรายงานเรา
- มีงานที่วิจารณ์เรื่องนี้ไว้แล้วไหม คำค้น: *data leakage in machine fault diagnosis*

### 3. ชุด feature ที่ใช้ เป็นชุดมาตรฐานไหม ขาดอะไร

เราเลือก 12 ตัวเอง โดยมีเงื่อนไขว่าต้องคำนวณบนไมโครคอนโทรลเลอร์ได้

**ที่ต้องไปหา** มาตรฐาน ISO ที่เกี่ยวข้อง (เช่น ISO 10816 / ISO 20816 เรื่องเกณฑ์
ระดับการสั่น) และงานทบทวนวรรณกรรมที่รวบรวมว่า feature ตระกูลไหนใช้กันบ้าง
เราอาจขาดตัวสำคัญไปโดยไม่รู้ตัว

### 4. การเลือกย่านความถี่สำหรับ envelope analysis

เราใช้ **2–5 kHz ตายตัว** โดยอ้างว่าเป็นย่านความถี่ธรรมชาติของโครงสร้าง
**แต่เราไม่เคยวัดว่าย่านนี้ถูกต้องสำหรับเครื่องนี้จริงไหม**

**ที่ต้องไปหา** มีวิธีเลือกย่านอัตโนมัติชื่อ **spectral kurtosis** และ **kurtogram**
ซึ่งหาย่านที่มีการกระแทกชัดที่สุดให้เอง ถ้าเป็นมาตรฐานจริง การใช้ย่านตายตัว
ของเราคือจุดอ่อนที่ต้องเขียนไว้ในรายงาน

### 5. ตรวจจับความผิดปกติโดยมีแต่ข้อมูลปกติ (ชั้นที่ 1)

เราวางแผนไล่จากเกณฑ์ทางสถิติ → Mahalanobis distance → Isolation Forest
โดยยังไม่มีงานวิจัยรองรับว่าลำดับนี้สมเหตุสมผล

**ที่ต้องไปหา** งานที่เปรียบเทียบวิธี novelty detection กับข้อมูลเครื่องจักรจริง
และดูว่าเขาวัดผลด้วยอะไรเมื่อไม่มีตัวอย่างของความเสียหาย

### 6. การสกัด feature บนไมโครคอนโทรลเลอร์

สถาปัตยกรรมของเราอยู่บนสมมติฐานว่า ESP32 คำนวณ FFT และ feature ได้ทันเวลา
ที่ความถี่การสุ่ม 20 kHz **ซึ่งเรายังไม่ได้วัดของจริงเลย**

**ที่ต้องไปหา** งานที่ทำ vibration feature extraction บน MCU จริง ดูว่าทำได้ที่
ความถี่เท่าไร ใช้หน้าต่างขนาดไหน และเจอข้อจำกัดอะไร

### 7. ลายเซ็นที่ปรากฏคนละฝั่งกับความเสียหาย

เราพบว่า **4 จาก 7 ลายเซ็นอยู่ที่เซ็นเซอร์ฝั่งตรงข้ามกับตลับลูกปืนที่เสีย**
และยังอธิบายไม่ได้ว่าเป็นการส่งผ่านการสั่นจริง หรือเป็นร่องรอยของรอบบันทึก

**ที่ต้องไปหา** งานที่ศึกษาการส่งผ่านการสั่นสะเทือนในเครื่องจักรหมุน
คำค้น: *vibration transmission path* หรือ *transfer path analysis*

## สิ่งที่เราทำมาแล้ว และน่าจะยังมีค่า

อาจารย์ท้วงเรื่องการอ้างอิง ไม่ได้บอกว่างานที่ทำมาผิด ของสองชิ้นนี้น่าจะยืนได้
และควรหางานวิจัยมายืนยันหรือหักล้าง

1. **พบว่าเอกสารของ MAFAULDA ระบุ sampling rate ผิด** (50 kHz → จริงคือ 51.2 kHz)
   ถ้าค้นแล้วไม่มีใครเคยรายงานไว้ นี่คือสิ่งที่มีค่าต่อคนที่ใช้ชุดข้อมูลนี้ต่อ
2. **วัดขนาดของ data leakage เป็นตัวเลขบนชุดข้อมูลเดียวกัน** (ต่างกัน 27 จุด)
   เป็นการสาธิตที่ชัดเจนและทำซ้ำได้
