## เขาทำอะไร

แก้ปัญหาที่ว่า **classifier แบบ supervised เมื่อเจอความเสียหายชนิดที่ไม่เคยเห็น
ตอนเทรน มันจะตอบผิดอย่างมั่นใจ** ซึ่งเป็นสถานการณ์จริงในโรงงาน เพราะไม่มีทาง
เก็บตัวอย่างความเสียหายได้ครบทุกชนิดก่อนติดตั้ง

วิธีของเขาคือต่อสองชั้นเข้าด้วยกัน

1. **ชั้นที่ 1 — supervised classifier** ทำนายคลาสความเสียหาย พร้อมคืน
   **posterior probability** (ความมั่นใจ) ออกมาด้วย
2. **ถ้าความมั่นใจ ≥ τ** → ตอบว่าเป็น `Known Fault` คลาสนั้นไปเลย
3. **ถ้าความมั่นใจ < τ** → **ส่งต่อให้ชั้นที่ 2** ซึ่งเป็น one-class detector
   ที่เทรนด้วย**ข้อมูลปกติเท่านั้น** แล้วชั้นที่ 2 ตัดสินว่าตัวอย่างนี้
   ยังอยู่ในขอบเขตของปกติ หรือหลุดออกไป

ผลลัพธ์จึงมี **3 ทาง** คือ `Normal Operation` / `Known Fault` / **`Unknown Anomaly`**

จุดขายคือ **เมื่อมีความเสียหายชนิดใหม่เกิดขึ้น ไม่ต้องเทรนชั้นที่ 2 ใหม่**
เพราะชั้นที่ 2 รู้จักแค่ปกติอย่างเดียว อะไรที่ไม่ปกติก็หลุดออกมาเองหมด

## ข้อมูลที่ใช้

**MAFAULDA ชุดเดียวกับเรา** 6 คลาส (normal, horizontal misalignment `mh`,
vertical misalignment `mv`, overhang bearing `ho`, underhang bearing `hu`,
imbalance `im`) ตรงกับที่เราแบ่งเป๊ะ

| หัวข้อ | ของเขา | ของเรา |
|---|---|---|
| sampling rate ที่ระบุ | **50 kHz** 🚩 | **51,200 Hz** (วัดเอง) |
| ช่องที่ใช้ | ทั้ง **8 ช่อง** รวม `tach` และ `mic` | 6 ช่องสั่นสะเทือน (ตัด `tach`/`mic`) |
| ขนาดหน้าต่าง | **ไม่ระบุ** 🚩 | 32,768 แถว (640 ms) |
| ความเร็วรอบ | **ไม่ใช้เลย** 🚩 | ใช้เป็นตัวควบคุมและส่งไปกับทุกข้อความ |
| มวลถ่วง 0/6/20/35 g | **ไม่พูดถึง** 🚩 | แยกชัด ใช้ 0 g เป็นโจทย์หลัก |

## วิธีการ

### feature — 286 มิติ

สกัดจากทั้ง 8 ช่อง รวมเป็นเวกเตอร์เดียว 286 ตัว

- **โดเมนเวลา** variance, standard deviation, RMS, peak-to-peak, **kurtosis**,
  **skewness**, **crest factor**
- **โดเมนความถี่** spectral variance, dominant frequency, **spectral entropy**,
  band-power ratios

**normalize ด้วยค่าสถิติจาก training partition เท่านั้น** และเขียนไว้ชัดว่าทำเพื่อ
*"preventing information leakage during model evaluation"*

### การแบ่ง train/test — จุดที่น่าสนใจที่สุดของงานนี้

เขาออกแบบ **41 experimental blocks** ขึ้นมาเอง (บอกตรงๆ ว่าเป็น contribution
ของงานนี้ ไม่ได้ลอกจากงาน MAFAULDA ก่อนหน้า) แต่ละ block คือการจับคู่คลาส
ที่ใช้เทรนกับที่ใช้ทดสอบแบบต่างกัน แบ่งเป็นสามฉากทัศน์

| ฉากทัศน์ | คลาสตอนทดสอบ | ตัวอย่าง block |
|---|---|---|
| **closed-set** | เหมือนตอนเทรนทุกคลาส | 1, 9, 13 |
| **partial open-set** | เป็น subset ของตอนเทรน | 2–7 |
| **fully open-set** | **ไม่มีอยู่ตอนเทรนเลย** | 3, 31, 35 |

จาก 41 block **แยก 8 block ไว้ปรับค่า τ** และ **33 block ที่เหลือใช้ประเมินผล
โดยไม่เคยมีส่วนร่วมในการเลือก τ เลย** กวาด τ ใน {0.50, …, 0.99} บน 8 block นั้น
ได้ **τ\* = 0.75**

### โมเดลที่เทียบ

| ชั้น | โมเดล |
|---|---|
| ชั้น 1 — ML | **Random Forest**, XGBoost, LightGBM, CatBoost, Decision Tree |
| ชั้น 1 — DL | **CNN**, RNN, LSTM |
| ชั้น 2 — one-class | **Isolation Forest**, Local Outlier Factor, One-Class SVM |

สถิติที่ใช้ตัดสิน **Friedman test** → **Nemenyi post-hoc** → **Wilcoxon signed-rank
พร้อม Bonferroni correction** → **Cliff delta** วัด effect size
ไม่ใช่แค่เอาค่าเฉลี่ยมาเทียบกันเฉยๆ

## ผลที่ได้

### 1. ML เท่ากับ DL — ไม่มีนัยสำคัญทางสถิติ

| โมเดล | F1 weighted |
|---|---:|
| CNN (DL ที่ดีที่สุด) | 0.7415 |
| **Random Forest (ML ที่ดีที่สุด)** | **0.7387** |

**Wilcoxon p = 0.538** (ไม่ต่างกัน) **Cliff delta = 0.054** (effect size ระดับ negligible)

เขาเลือก **Random Forest** เป็นโมเดลสุดท้าย ด้วยเหตุผล **ความทนทาน +
ดู feature importance ได้ + ต้นทุนการคำนวณต่ำ**

### 2. Isolation Forest ชนะ one-class ตัวอื่นชัด

| โมเดล | F1 weighted | Friedman rank |
|---|---:|---:|
| **Isolation Forest** | **0.949 ± 0.028** | **1.29** |
| LOF / OC-SVM | ต่ำกว่า | สูงกว่า |

เหตุผลที่เขายกให้ Isolation Forest คือ **linear time complexity และใช้หน่วยความจำน้อย
จึงเหมาะกับ industrial monitoring ที่ข้อมูลไหลเข้าต่อเนื่อง**

### 3. ต่อสองชั้นแล้วดีขึ้นจริง

เทียบกับ supervised ชั้นเดียวล้วนบน block เดียวกัน

| ตัวชี้วัด | ส่วนต่าง | p |
|---|---:|---|
| F1 weighted | **+9.10 จุด** | < 0.001 |
| Cohen kappa | +0.191 | < 0.001 |
| MCC | +0.168 | < 0.001 |

อัตราที่ตัวอย่างถูกส่งต่อไปชั้นที่ 2 (**routing rate**) แกว่งตั้งแต่ **1% ถึง 90%**
ขึ้นกับว่า block นั้น open-set มากแค่ไหน — สมเหตุสมผล

## 🚩 เทียบกับของเรา

### ✅ สนับสนุน (5 ข้อ)

**1. สนับสนุนการเลือก Random Forest ของเรา ด้วยเหตุผลคำเดียวกัน**

เราเขียนใน proposal §5.6.1 ว่าเลือก Random Forest เพราะทนทาน ดู feature importance ได้
และคำนวณเบาพอสำหรับ Pi **เขาเลือกด้วยเหตุผลสามข้อเดียวกันเป๊ะ** และมี Friedman +
Wilcoxon + Cliff delta รองรับว่าไม่ได้แพ้ CNN **นี่คือการอ้างอิงที่ตอบอาจารย์ได้ตรงที่สุด
ว่าทำไมไม่ใช้ deep learning**

**2. สนับสนุนว่าไม่จำเป็นต้องใช้ deep learning เมื่อสกัด feature ไว้ดีแล้ว**

ซึ่งเป็นสมมติฐานที่สถาปัตยกรรมทั้งหมดของเราตั้งอยู่บนนั้น (ESP32 สกัด feature →
Pi ทำ inference) ถ้าข้อนี้ผิด แผนทั้งหมดต้องเปลี่ยน **ตอนนี้มีงานตีพิมพ์รองรับแล้ว**
(แต่ดูข้อจำกัดของข้ออ้างนี้ในหัวข้อจุดอ่อนข้อ 1 ด้วย)

**3. ✅ ตอบคำถามข้อ 5 ใน README ได้ — Isolation Forest คือเป้าหมายที่ถูก**

เราวางลำดับไว้ว่า เกณฑ์สถิติ → Mahalanobis → **Isolation Forest** โดยยังไม่มีอะไรรองรับ
เขาเทียบ Isolation Forest / LOF / OC-SVM บน MAFAULDA แล้ว **Isolation Forest ชนะที่
F1w 0.949** → ปลายทางที่เราเล็งไว้ถูกแล้ว ส่วนการไล่จากง่ายไปยากยังเป็นข้อดีของเรา
ในแง่อธิบายได้ ซึ่งงานนี้ไม่ได้พูดถึง

**4. สนับสนุนการแยกเป็นสองชั้นที่ใช้วิธีคนละแบบ**

ตอนที่พบว่า §5.6 ขัดกับ §7.4.4 เราแก้โดยแยกเป็นชั้นที่ 1 (เทรนจากข้อมูลปกติเท่านั้น)
กับชั้นที่ 2 (supervised จำแนกชนิด) **โครงนี้ตรงกับของเขา** ต่างกันแค่ลำดับ
ของเขาเอา supervised ไว้หน้า ของเราเอา anomaly detection ไว้หน้า

**5. สนับสนุนความระแวงของเราเรื่องตัวเลขสวยเกินจริง**

**เขารายงาน F1w ประมาณ 0.74 บน open-set ไม่ใช่ 99%** และระบุโปรโตคอลกันรั่วไว้ชัด
(normalize ด้วยสถิติจาก train เท่านั้น, แยก calibration block ออกจาก evaluation block)
→ **ยืนยันว่าคำเตือนที่เราเขียนไว้ท้าย `paper/README.md` ถูกต้อง** งานที่ทำอย่างระวัง
บน MAFAULDA ได้เลขระดับ 0.7 ไม่ใช่ 0.99

### 🔄 ต้องเปลี่ยนของเรา (2 ข้อ)

**6. 🔥 แผนของเราขาดช่องทาง "ผิดปกติแต่ไม่รู้ว่าอะไร" — ของเขาแก้ไว้แล้ว**

นี่คือสิ่งที่มีค่าที่สุดที่ได้จากงานนี้ ออกแบบของเราตอนนี้มีชั้นที่ 1 บอกว่าผิดปกติ
และชั้นที่ 2 บอกว่าผิดปกติแบบไหน **แต่เราไม่เคยออกแบบว่าจะทำอย่างไรเมื่อชั้นที่ 1
เตือนแล้วชั้นที่ 2 จำแนกไม่ได้** ซึ่งจะเกิดขึ้นแน่นอนที่หน้างาน เพราะเครื่องจักรจริง
มีความเสียหายชนิดที่ MAFAULDA ไม่มี (เช่น BPFI ที่ dataset นี้ไม่มีเลย)

**กลไก confidence routing ด้วย threshold τ ของเขาแก้ปัญหานี้ตรงๆ** และผลลัพธ์
สามทาง `Normal / Known Fault / Unknown Anomaly` คือสิ่งที่ควรเอามาใส่ใน
`docs/data-pipeline-design.md` และ topic `alert`

**7. ชุด feature ของเราขาด skewness และ spectral entropy**

ของเรา 72 ตัว (12 × 6 ช่อง) ของเขา 286 ตัว สองตัวที่เขามีแต่เราไม่มีและ
**คำนวณบน ESP32 ได้ทั้งคู่** คือ

- **skewness** โมเมนต์ที่ 3 คำนวณพร้อม kurtosis ได้แทบฟรี
- **spectral entropy** วัดว่าพลังงานกระจายทั่วแถบหรือกระจุกที่พีค ต้องมี FFT
  อยู่แล้วซึ่งเรามี

→ **ควรเพิ่มเข้า `src/features/feature_grid.py` แล้วลองดูใน `bubble_grid.py`**
อาจช่วยเรื่อง overhang cage ที่ยังไม่มีลายเซ็นเลย

### ⬜ ไม่เกี่ยว / ตอบไม่ได้ (2 ข้อ)

**8. ❌ ตอบคำถามข้อ 1 (order tracking) ไม่ได้ — เพราะเขาก็ไม่ได้ทำ**

ค้นทั้งฉบับแล้ว **คำว่าความเร็วรอบปรากฏเพียงสามครั้ง** และไม่มี order tracking
หรือ angular resampling เลย `tach` ถูกรวมเข้าไปในเวกเตอร์ feature เฉยๆ
โดยไม่ได้แปลงเป็นความเร็ว และ**ไม่ได้ใช้ความเร็วเป็นตัวควบคุมการแบ่งข้อมูล**

เขาเขียนเรื่อง *"varying load and speed conditions"* ไว้ใน **future work** เท่านั้น

> **นี่กลายเป็นข้อดีของเราโดยไม่ตั้งใจ** เราวัดได้ว่าตัวชี้วัดบน `o_axial`
> กระโดด 4 เท่าเมื่อความเร็วข้าม 50 Hz และวัดได้ว่าการแบ่งแบบ by-speed
> ทำให้ accuracy ตก 11 จุดจาก by-file งานที่ตีพิมพ์ใน IEEE Access ปี 2026
> ยังไม่ได้จัดการเรื่องนี้ **คำถามข้อ 1 ยังเปิดอยู่ ต้องหางานอื่นมาตอบ**

**9. 🚩 เขาระบุ sampling rate = 50 kHz ซ้ำความผิดพลาดของเอกสารต้นทาง**

หน้า 7 เขียนตรงๆ ว่า *"acquired at a sampling rate of 50 kHz"* ซึ่งเราพิสูจน์แล้ว
ว่าผิด ค่าจริงคือ 51,200 Hz (ดู `experiments/2026-09-20-sampling-rate.md`)

ผลกระทบกับงานของเขา **จำกัด** เพราะ feature ความถี่ที่เขาใช้ส่วนใหญ่เป็นอัตราส่วน
(band-power ratios) และ spectral entropy ซึ่งคลาด 2.4% แล้วแทบไม่เปลี่ยนค่า
**แต่ `dominant frequency` ที่เขาใช้จะคลาดไป 2.4% อย่างเป็นระบบทุกตัวอย่าง**

> **ยืนยันว่าข้อค้นพบเรื่อง sampling rate ของเรามีค่าจริง** งานที่ตีพิมพ์ใน
> วารสาร IEEE ปี 2026 บนชุดข้อมูลเดียวกันยังคัดลอกค่าผิดนี้มา ซึ่งเป็นสัญญาณว่า
> **ยังไม่มีใครรายงานไว้** → ควรเขียนเป็นหัวข้อหนึ่งในรายงานสหกิจ

## สิ่งที่ควรเอามาใช้

เรียงตามลำดับที่ควรทำ

1. **เพิ่มทางออกที่สามคือ `unknown` เข้าไปในออกแบบ** แก้ `docs/data-pipeline-design.md`
   ให้ `_evaluate()` ใน `src/service/ingest.py` (ยังเป็น stub) คืนค่าได้สามแบบ
   และเพิ่ม field `confidence` กับ `routed` ลงใน message ของ topic `alert`
2. **อ้างอิงงานนี้ใน proposal §5.6.1** แทนที่จะเขียนว่าเลือก Random Forest เพราะ…
   เฉยๆ ให้อ้างได้ว่ามีงานที่เทียบกับ CNN/RNN/LSTM บน MAFAULDA แล้วไม่ต่างกัน
   อย่างมีนัยสำคัญ (p = 0.538)
3. **อ้างอิงงานนี้สำหรับ Isolation Forest** ในชั้นที่ 1 แทนที่จะเดาว่าน่าจะดี
4. **เพิ่ม skewness และ spectral entropy เข้า `feature_grid.py`** แล้วรันใหม่
   (15.5 นาที) ลองดูใน `bubble_grid.py` ว่าช่วย overhang cage ไหม
5. **ยืมสามฉากทัศน์ของเขามาใช้ประเมิน** closed-set / partial open-set / fully open-set
   เป็นกรอบที่ชัดและอธิบายให้อาจารย์ฟังง่ายกว่าที่เราเขียนอยู่
6. **ยืมชุดตัวชี้วัด** เขาใช้ F1 weighted + Cohen kappa + MCC + ROC-AUC
   ซึ่ง **MCC และ kappa เหมาะกับข้อมูลที่คลาสไม่สมดุล** และเราไม่ได้ใช้เลย

## จุดอ่อนของงานนี้

อ่านอย่างมีวิจารณญาณ ไม่ใช่เชื่อทุกอย่าง

**1. 🚩 CNN ของเขาไม่ได้กิน raw signal — กินเวกเตอร์ 286 มิติเหมือนกันหมด**

เขียนไว้ตรงๆ ว่า *"consume the same 286-dimensional standardised feature vector …
(not raw signal segments)"*

**ข้อสรุป "ML เท่ากับ DL" จึงแคบกว่าที่พาดหัวชวนให้คิด** มันพิสูจน์แค่ว่า
*DL บน feature ที่คนสกัดไว้แล้ว* ไม่ชนะ *ML บน feature ชุดเดียวกัน* ซึ่งไม่น่า
แปลกใจเลย ส่วนข้ออ้างที่แรงกว่าในวงการคือ DL บน **raw waveform** เรียน feature
ได้เองดีกว่าคนสกัด — **งานนี้ไม่ได้ทดสอบข้อนั้น**

⚠️ เวลาอ้างอิงในรายงาน **ต้องเขียนให้ตรงว่าเขาเทียบอะไรกับอะไร** ไม่ใช่เขียนลอยๆ
ว่ามีงานยืนยันว่า ML ไม่แพ้ DL

**2. 🚩 ไม่ระบุขนาดหน้าต่างเลย**

ค้นทั้งฉบับแล้วมีแค่คำว่า *"for each signal window"* โดยไม่บอกว่ากี่แถวหรือกี่
มิลลิวินาที → **ทำซ้ำไม่ได้** และ **ตรวจไม่ได้ว่าหน้าต่างจากไฟล์เดียวกันไปโผล่
ทั้ง train และ test ภายใน block เดียวกันหรือเปล่า** ซึ่งคือ leakage ช่องทาง
ที่เราวัดได้ว่ากินถึง 15 จุด (0.996 → 0.843)

เขากัน leakage ไว้สองชั้นคือ normalize ด้วยสถิติจาก train และการแยก calibration
block **แต่ไม่ได้พูดถึงการแบ่งภายใน block เลย** นี่เป็นช่องที่เราอาจทำได้ดีกว่าเขา

**3. ไม่แจกแจง recall ตามชนิดความเสียหาย**

รายงานแต่ F1 weighted กับ macro เราวัดเองแล้วว่า **ball fault ตรวจง่ายกว่า
cage fault มาก** (envelope floor สูงกว่า normal 7 เท่า เทียบกับ cage ที่จับไม่ได้เลย)
ตัวเลขรวมจึงกลบเรื่องนี้

**4. ไม่แยกมวลถ่วง 0/6/20/35 g**

ซึ่งเป็นกับดักใหญ่ที่สุดของ MAFAULDA เอกสารต้นทางบอกเองว่าความเสียหายตลับลูกปืน
แทบมองไม่เห็นเมื่อไม่มี imbalance **ถ้าเขาใช้ไฟล์มวลมากกว่า 0 g ปนมา โมเดลอาจเรียน
imbalance แทน bearing fault** เขาไม่ได้พูดถึงเรื่องนี้เลย

**5. ใช้ hyperparameter ค่าเริ่มต้นของ scikit-learn** (เขายอมรับเองใน limitations)

**6. calibration set มีแค่ 8 block** เล็กสำหรับการเลือก τ (เขายอมรับเองด้วย)

**7. รวมทุกความเสียหายที่ไม่รู้จักเป็นคลาสเดียว** `Unknown Anomaly` ไม่ได้แยกว่า
เป็นชนิดไหน (เขายอมรับเอง) สำหรับงานเราที่ต้องบอกช่างซ่อมว่าให้ไปดูอะไร
ข้อนี้สำคัญ

**8. ห้องแล็บล้วน ไม่มีข้อมูลหน้างานจริง** และใช้เซ็นเซอร์ชนิดเดียว (เขายอมรับเอง)
