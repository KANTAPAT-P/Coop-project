# พิสูจน์ sampling rate ใหม่ด้วยชื่อไฟล์ — ไม่พึ่ง tachometer เลย

**วันที่** 2026-10-02
**เหตุที่ทำ** หลังอ่านงานวิจัย 11 ฉบับพบว่า **8 ฉบับระบุ 50 kHz** จึงเกิดคำถามว่า
*"หรือจริงๆ เราผิด เพราะใครๆ เขาก็นับได้ 50 kHz"* ซึ่งเป็นคำถามที่ถูกต้องและต้องตอบ
เพราะ `fs` เป็นค่าคงที่ที่กระทบทุกอย่างในโปรเจกต์

**ผล: ยืนยันว่า fs = 51,200 Hz ด้วยหลักฐานที่แข็งกว่าเดิมมาก และพบว่าทั้ง 8 ฉบับ
ไม่ได้วัดเอง แต่ลอกมาจากเอกสารต้นทางทั้งหมด**

---

ตรวจบริบทของประโยคที่ระบุ 50 kHz ในทุกฉบับ **ทุกฉบับอยู่ในหัวข้อ
"Dataset Description" และอ้างอิงกลับไปที่ตัว dataset**

| 10 Kim | *"MAFAULDA dataset **[3]** contains 1,951 five-second records sampled at 50 kHz"* | [3] = MAFAULDA |
| 02 Costa | หัวข้อ IV-A Dataset | [29] = MAFAULDA |

**ไม่มีฉบับใดวัดอัตราการสุ่มเอง ไม่มีฉบับใดตรวจสอบมัน**
ทั้ง 8 ฉบับเป็นการเล่าซ้ำข้อความเดียวจากหน้าเว็บของ dataset

> **บทเรียน** ความเห็นพ้องของงานหลายฉบับมีน้ำหนักเฉพาะเมื่อแต่ละฉบับ

> ของหลักฐานเลย — มันคือหลักฐานชิ้นเดียวที่ถูกนับซ้ำ 8 ครั้ง

## 2. การพิสูจน์ใหม่ — ชื่อไฟล์คือดัชนีช่อง FFT

### แนวคิด

การพิสูจน์เดิม (`2026-09-20-sampling-rate.md`) ใช้การนับพัลส์ tachometer
เทียบกับชื่อไฟล์ ซึ่ง**พึ่งโค้ดที่เราเขียนเอง** และพึ่งสมมติฐานว่าชื่อไฟล์คือ
ความเร็วจริง (ไม่ใช่ค่าที่ตั้งไว้ซึ่งอาจต่างจากของจริงเพราะ slip)

การพิสูจน์ใหม่**ไม่พึ่งอะไรเลยนอกจากเลขคณิตบนชื่อไฟล์**

ถ้าคนทำ dataset หาความเร็วรอบด้วย **FFT ของช่อง tachometer บนทั้งไฟล์**
(250,000 แถว) แล้วตั้งชื่อไฟล์ตามความถี่ของช่อง (bin) ที่เจอ
**ชื่อไฟล์ทุกไฟล์ต้องเป็นจำนวนเต็มเท่าของความละเอียด FFT**

```
ความละเอียด FFT = fs / 250,000

fs = 51,200  ->  0.2048 Hz
fs = 50,000  ->  0.2000 Hz
```

### ผล — ชี้ไปทางเดียว ไม่มีความกำกวม

ทดสอบกับ **ชื่อไฟล์ที่ไม่ซ้ำกันทั้ง 246 ชื่อ** ในทั้ง dataset

| fs ที่สมมติ | ความละเอียด FFT | ชื่อไฟล์ที่ลงตัวพอดี | |
|---:|---:|---|---|
| **51,200 Hz** | 0.204800 Hz | **246 / 246 = 100.00%** | ✅ |
| 50,000 Hz | 0.200000 Hz | 2 / 246 = 0.81% | ❌ |
| 51,000 Hz | 0.204000 Hz | 1 / 246 = 0.41% | ❌ |
| 51,712 Hz | 0.206848 Hz | 3 / 246 = 1.22% | ❌ |
| 48,000 Hz | 0.192000 Hz | 17 / 246 = 6.91% | ❌ |
| 65,536 Hz | 0.262144 Hz | 8 / 246 = 3.25% | ❌ |

เกณฑ์ที่ใช้คือคลาดจากจำนวนเต็มไม่เกิน 1 × 10⁻⁶

### ดูตัวเลขจริงแล้วชัดกว่าตาราง

| ชื่อไฟล์ | ÷ 0.2048 | ÷ 0.2000 |
|---:|---:|---:|
| 12.0832 | **59.0000** | 60.4160 |
| 12.288 | **60.0000** | 61.4400 |
| 12.4928 | **61.0000** | 62.4640 |
| 12.6976 | **62.0000** | 63.4880 |
| 12.9024 | **63.0000** | 64.5120 |
| 13.1072 | **64.0000** | 65.5360 |
| 37.2736 | **182.0000** | 186.3680 |
| 37.4784 | **183.0000** | 187.3920 |
| 61.6448 | **301.0000** | 308.2240 |
| 62.2592 | **304.0000** | 311.2960 |

**หารด้วย 0.2048 แล้วได้จำนวนเต็มเรียงติดกัน 59, 60, 61, 62, 63, 64 …
182, 183, 184 … 301, 302, 303, 304**

นี่ไม่ใช่เรื่องบังเอิญได้ ในช่วง 12–62 Hz มีค่าทศนิยม 4 ตำแหน่งอยู่ 500,000 ค่า
แต่มีค่าที่เป็นจำนวนเต็มเท่าของ 0.2048 อยู่เพียง ~244 ค่า
**โอกาสที่ชื่อไฟล์หนึ่งชื่อจะลงตัวโดยบังเอิญคือ 0.05% และต้องลงตัวพร้อมกัน 246 ชื่อ**

ตรวจซ้ำได้ด้วยสคริปต์ที่ใช้ในการทดลองนี้ (อ่านแค่ชื่อไฟล์ ไม่ต้องอ่านข้อมูล
รันเสร็จในไม่ถึงวินาที)

## 3. การพิสูจน์ชั้นที่สอง — คำนวณ fs ออกมาตรงๆ โดยไม่สมมติ fs

### แนวคิด

**ดัชนีของช่อง FFT (`k`) เป็นจำนวนเต็มที่อ่านได้จากข้อมูลโดยไม่ต้องรู้ `fs` เลย**
เพราะมันคือตำแหน่งในอาเรย์ ไม่ใช่ความถี่

```
ความถี่จริง = k × fs / N        ->        fs = ความถี่จริง × N / k
```

ดังนั้นถ้ารู้ `k` (จากข้อมูล) และรู้ความถี่จริง (จากชื่อไฟล์) ก็**คำนวณ `fs`
ออกมาได้ตรงๆ ไม่ต้องเดา ไม่ต้องเทียบกับค่าที่สมมติไว้ก่อน**

### ผล

ทดสอบ 24 ไฟล์ สุ่มคลาสละ 4 ไฟล์ ครบทั้ง 6 คลาส

| | ผล |
|---|---|
| ไฟล์ที่ได้ **51,200.00 Hz พอดี** | **18 / 24** |
| ไฟล์ที่เหลือ 6 ไฟล์ | 51,403 – 51,579 Hz |
| **ค่าต่ำสุดจากทั้ง 24 ไฟล์** | **51,200.00 Hz** |
| คลาดจาก 51,200 | **+0.0000 %** (ค่ากลาง) |
| คลาดจาก 50,000 | **+2.4000 %** |

**6 ไฟล์ที่ไม่ลงพอดีคือข้อจำกัดของตัวหาพีคที่เขียนแบบง่ายๆ ไม่ใช่ข้อมูล**
พัลส์ tachometer เป็นคลื่นสี่เหลี่ยมซึ่งมีฮาร์มอนิกแรงมาก บางไฟล์ `argmax`
จับฮาร์มอนิกที่ 2 แทนตัวมูลฐาน แก้ด้วยการเลือกพีคที่ความถี่ต่ำสุดที่ยังสูงเกิน
40% ของพีคสูงสุด ซึ่งบางครั้งไปจับ sidelobe ที่ห่างออกไป **หนึ่งช่อง**

ผลที่เกิดขึ้นคือ `k` เล็กไป 1 ทำให้ `fs` ที่คำนวณได้**สูงเกินไปเล็กน้อย**
ซึ่งอธิบายได้ว่าทำไมทั้ง 6 ไฟล์จึงอยู่เหนือ 51,200 ทั้งหมด ไม่มีไฟล์ไหนต่ำกว่า

**จุดสำคัญ** 50,000 Hz ห่างจาก 51,200 Hz อยู่ **2.4% ซึ่งเท่ากับ ~12 ช่องความถี่**
ความผิดพลาดระดับหนึ่งช่องไม่มีทางไปถึงได้ **ไม่มีไฟล์ใดเลยที่ชี้ไปทาง 50,000 Hz**

## 4. หลักฐานจากฮาร์ดแวร์

NI 9234 ใช้ timebase 13.1072 MHz และ sampling rate ที่เลือกได้คือ

```
fs = 13,107,200 / (256 × n)        n = 1, 2, 3, ...

n = 1  ->  51,200 Hz      <- ค่าสูงสุด
n = 2  ->  25,600 Hz
n = 3  ->  17,066.67 Hz
```

**50,000 Hz ไม่อยู่ในรายการนี้** เพราะ 51,200 / 50,000 = 1.024 ไม่ใช่จำนวนเต็ม
→ **อุปกรณ์ที่ dataset ระบุว่าใช้ สุ่มที่ 50,000 Hz ไม่ได้ตั้งแต่ต้น**

⬜ **ยังควรตรวจ** ตัวเลข timebase 13.1072 MHz มาจากความเข้าใจเรื่องสเปกของ
NI 9234 ควรยืนยันกับ datasheet ของ National Instruments โดยตรงก่อนเขียนลงรายงาน
แต่ข้อที่ยืนยันแล้วคือ **51.2 kHz เป็นอัตราสูงสุดของ NI 9234** ซึ่งตรงกับ
รายการอุปกรณ์ของ dataset เอง และ **ฉบับ 07 (Tran 2023) ก็เขียนตัวเลขนี้ไว้**
〔หน้า 2〕 ว่า *"two National Instruments NI 9234 ... with a sample rate of 51 200 Hz"*

## 5. ทำไมเอกสารต้นทางจึงเขียน 50 kHz

สมมติฐานที่เข้ากับหลักฐานทุกชิ้น

1. ตั้ง NI 9234 ที่อัตราสูงสุด = **51,200 Hz**
2. บันทึก **250,000 แถว** = 4.8828 วินาที
3. หาความเร็วรอบด้วย FFT ของ tachometer ได้ `k × 0.2048 Hz` → ใช้ตั้งชื่อไฟล์
4. เขียนเอกสารโดย**ปัดเป็นเลขกลมๆ** ว่า "50 kHz, 5 วินาที"

ข้อ 4 ไม่ใช่เรื่องแปลก เพราะ "51.2 kHz ยาว 4.8828 วินาที" อ่านยากกว่า
"50 kHz ยาว 5 วินาที" มาก และ **250,000 ÷ 50,000 = 5 พอดี** ซึ่งทำให้ตัวเลข
ที่ปัดแล้วดูสอดคล้องกันเอง จึงไม่มีใครสะดุด

**ฉบับ 07 เป็นหลักฐานว่ากลไกนี้เกิดขึ้นจริง** เพราะเขาเขียนทั้ง 51,200 Hz
(สเปกโมดูล) และ 50,000 Hz (อัตราของข้อมูล) ไว้ใน**หน้าเดียวกัน ห่างกัน 18 บรรทัด**
โดยไม่สังเกตว่ามันขัดกัน

### ข้ออ่อนที่ยังเหลือ และเหตุที่ไม่ทำให้ข้อสรุปเปลี่ยน

หลักฐานทุกข้อยังตั้งอยู่บนสมมติฐานว่า **ชื่อไฟล์คือความเร็วรอบจริง**
ถ้าชื่อไฟล์เป็นค่าอื่น (เช่นค่าที่ตั้งบนตัวควบคุมมอเตอร์) ข้อสรุปจะสั่น

**แต่หลักฐานข้อ 1 ปิดช่องนี้ไปแล้ว** เพราะค่าที่ตั้งบนตัวควบคุมมอเตอร์
ไม่มีเหตุผลใดที่จะเป็นจำนวนเต็มเท่าของ 0.2048 Hz ครบทั้ง 246 ค่า
ตัวเลข 0.2048 เกิดจาก `fs/250000` ซึ่งเป็นสมบัติของ**การประมวลผลสัญญาณ**
ไม่ใช่สมบัติของมอเตอร์ **ชื่อไฟล์จึงต้องถูกคำนวณจากข้อมูลที่สุ่มมาที่ 51,200 Hz**

## 7. ข้อสรุป

**fs = 51,200 Hz ยืนยันแล้ว ไม่ต้องสงสัยต่อ**

และ**การที่ 8 ฉบับเขียน 50 kHz ไม่ใช่หลักฐานค้าน** เพราะทั้ง 8 ฉบับ
ลอกมาจากแหล่งเดียวกันโดยไม่มีใครตรวจ

ข้อนี้เลื่อนสถานะจาก "ข้อค้นพบที่น่าจะมีค่า" เป็น **"ข้อค้นพบที่ควรเขียน
เป็นหัวข้อหนึ่งในรายงานสหกิจ"** เพราะมีผลต่องานของคนอื่นด้วย
ถ้า 8 ฉบับใช้ค่าผิด แกนความถี่ของกราฟในงานเหล่านั้นคลาดไป 2.4% ทั้งหมด
