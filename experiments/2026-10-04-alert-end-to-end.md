# ทดสอบผลการประเมินทั้งเส้นทางผ่าน broker จริง และเพิ่มแผงในแดชบอร์ด

**วันที่** 2026-10-04
**ทำอะไร** ปิดงานที่ค้างจาก `...-alert-service-integration.md` คือทดสอบผ่าน
Mosquitto จริงแทนการจำลอง และเพิ่มแผงแสดงผลการประเมินใน Grafana

---

## 🚨 ช่องว่างที่เจอทันทีที่ทดสอบจริง

ทดสอบรอบแรกผ่านได้หมด **ข้อความ `alert` ออกมาจาก broker ครบ 420 ข้อความ**
แต่พอไปตรวจว่าแดชบอร์ดแสดงได้ไหม พบว่า

```
measurements ใน InfluxDB:  device_status, vibration
```

**ไม่มี `assessment` เลย** เพราะ `_evaluate()` ส่งผลเข้า MQTT อย่างเดียว
ไม่ได้เขียนลงฐานข้อมูล

**Grafana อ่านจาก InfluxDB ไม่ได้อ่านจาก MQTT** ผลการประเมินจึง**ไม่มีทาง
ขึ้นแดชบอร์ดได้เลย** ไม่ว่าจะเพิ่มแผงยังไงก็ตาม

> **บทเรียน: ระบบที่ "ทำงานได้" ในความหมายว่าข้อความไหลครบ ยังอาจใช้งานไม่ได้
> ถ้าข้อมูลไม่ไปอยู่ในที่ที่คนดูเปิดดู** การทดสอบที่จบแค่ "ส่งแล้วถึง"
> จึงไม่พอ ต้องตามไปจนถึงหน้าจอที่คนใช้จริง

**แก้โดย** เพิ่ม measurement `assessment` ใน `ingest.py` เขียนคู่ไปกับการ
publish ทุกครั้ง โดย `verdict` และ `severity` เป็น tag (ค่าเป็นชุดจำกัด 4 และ 3)
ส่วนคะแนนและค่าสถิติเป็น field ตามกฎใน `docs/data-pipeline-design.md` §6

เขียน `threshold` ลงไปด้วย เพื่อให้ย้อนดูได้ว่าตอนนั้นใช้เกณฑ์อะไร

## ผลการทดสอบทั้งเส้นทาง

```
simulate.py  --interval 0.4 --limit 60    (6 เครื่อง x 60 รอบ)
      |  MQTT
Mosquitto  localhost:1883
      |
ingest.py  --seconds 40
      |--> InfluxDB   measurement vibration + assessment
      |--> MQTT       pdm/<site>/<area>/<machine>/alert
Grafana  <-- InfluxDB
```

|---|---:|
| ส่งจากสคริปต์จำลอง | 372 |
| broker ตอบรับ | **372 (100.0%)** |
| ingest รับได้ | 378 (รวม status 18) |
| เขียน `vibration` | 360 |
| **publish `alert`** | **360** |
| **เขียน `assessment`** | **360** |
| ข้อความที่ตรวจไม่ผ่าน | **0** |

### ผลการประเมิน

| verdict | จำนวน |
|---|---:|
| `normal` | 93 |
| `unknown_anomaly` | 260 |
| `indeterminate` | 7 |

7 ข้อความที่เป็น `indeterminate` คือ `out_of_speed_range` เพราะความเร็วของ
สคริปต์จำลองแกว่งตามคลื่นไซน์จนออกนอกช่วง 13.1–60.4 Hz ที่เส้นฐานครอบคลุม
**ซึ่งเป็นพฤติกรรมที่ถูกต้อง** ระบบบอกว่าตรวจไม่ได้ แทนที่จะเดา

### 🎯 ผลที่สำคัญที่สุด — แยกเครื่องปกติออกจากเครื่องที่เสียได้

วัดจาก `is_anomaly` เฉลี่ยต่อเครื่อง จาก 60 ข้อความต่อเครื่อง

| เครื่อง | คลาสที่จำลอง | สัดส่วนที่ถูกตัดสินว่าผิดปกติ |
|---|---|---:|
| **motor-01** | **normal** | **0.00** ✅ |
| motor-02 | imbalance | 0.95 |
| motor-03 | horizontal-misalignment | 0.53 |
| motor-04 | vertical-misalignment | 0.97 |
| motor-05 | underhang bearing | 0.98 |
| motor-06 | overhang bearing | 0.90 |

**motor-01 ไม่ถูกเตือนเลยแม้แต่ครั้งเดียวจาก 60 ข้อความ** ขณะที่เครื่องที่เสีย
ทั้งห้าเครื่องติด 53–98%

**motor-03 ที่ 0.53 เป็นตัวที่อ่อนที่สุด ซึ่งตรงกับผลออฟไลน์** ที่วัดได้ว่า
h-misalignment 0.5 mm มี recall เพียง 0.438 จึงไม่ใช่เรื่องผิดคาด

### ตัวอย่างข้อความ `alert` จริงจาก broker

เครื่อง motor-02 ซึ่งจำลองคลาส imbalance

```json
{
  "verdict": "unknown_anomaly", "severity": "alarm",
  "score": 41.781, "n_exceed": 35,
  "evidence": [
    {"feature": "o_radial.h1_frac", "z": 41.78},
    {"feature": "u_axial.h1_frac",  "z": 29.85},
    {"feature": "u_radial.h1_frac", "z": 29.67}
  ],
  "gate": {"votes": 1, "needed": 4, "window": 1},
  "context": {"rot_hz": 51.696, "rot_quality": "ok"},
  "caveats": ["immediate_hard_threshold"]
}
```

🎯 **ตัวชี้วัดสามอันดับแรกเป็น `h1_frac` ทั้งหมด ซึ่งคือสัดส่วนพลังงานที่ 1×
และเป็นลายเซ็นของ imbalance ที่ `CLAUDE.md` หัวข้อ 5 ระบุไว้พอดี**

ระบบไม่ได้แค่บอกว่าผิดปกติ แต่ชี้ไปที่ตัวชี้วัดที่ถูกต้องตามทฤษฎีด้วย
โดยที่**ไม่เคยเห็นข้อมูล imbalance ตอนเทรนเลย** เพราะเทรนจากคลาส normal
อย่างเดียว

`caveats: immediate_hard_threshold` แปลว่า score 41.8 สูงเกิน `hard_z` = 37.6
จึงเตือนทันทีโดยไม่รอด่านยืนยันซ้ำ ซึ่งเป็นพฤติกรรมที่ตั้งใจ

### topic ที่ออกมาจริง

```
pdm/plant1/press-line/motor-01/alert ... motor-06/alert
```

**ทั้งหมดเป็นค่าดิบ คนดูต้องตีความเองว่าผิดปกติหรือยัง ซึ่งเป็นงานของระบบ**

### เพิ่มอีก 4 แผง รวมเป็น 12

| แผง | ตอบคำถาม |
|---|---|
| **คะแนนความผิดปกติ เทียบกับเกณฑ์** | ค่าที่เห็นเกินเกณฑ์หรือยัง — **มีเส้นแดงบนกราฟ** |

| จำนวนข้อความที่ผิดปกติ รวมรายชั่วโมง | **มีทิศทางไหม** ตามที่อาจารย์ชี้ |
| ค่าสถิติแนวโน้ม Mann-Kendall (tau) | แนวโน้มเป็นตัวเลข |

### รายละเอียดที่ตั้งใจทำ

**เส้นเกณฑ์อ่านจากไฟล์โมเดล ไม่ได้เขียนเลขตายตัว**
ถ้าเทรนใหม่จนเกณฑ์เปลี่ยนแล้วเส้นบนกราฟยังเป็นเลขเดิม **เส้นนั้นจะโกหก
ซึ่งแย่กว่าไม่มีเส้นเลย** `make_dashboard.py` จึงอ่าน `vote_min` จาก
`models/baseline-normal.json` ตอนสร้างไฟล์ และเตือนถ้าอ่านไม่ได้

**แผงคะแนนย่อด้วย `max` ไม่ใช่ `mean`**
แดชบอร์ดติดตามสภาพ**ต้องเปิดเผยปัญหา ไม่ใช่กลบด้วยค่าเฉลี่ย**
ถ้าในช่วงย่อยหนึ่งมีข้อความผิดปกติอยู่ข้อความเดียว ต้องเห็นมัน
หลักเดียวกับที่แผงคุณภาพความเร็วรอบใช้ `min`

**แผงนับรายชั่วโมงตรึง `every: 1h` ไม่ใช้ `v.windowPeriod`**
เพราะ**หน่วยของแกนต้องคงที่** ถ้าปล่อยให้เปลี่ยนตามช่วงเวลาที่ผู้ใช้เลือก
ความสูงของแท่งจะเปลี่ยนทั้งที่ข้อมูลเท่าเดิม แล้วการเทียบว่าแนวโน้มสูงขึ้น
หรือไม่จะเชื่อถือไม่ได้ ซึ่งทำลายจุดประสงค์ของแผงนี้ทั้งหมด

**แผงสถานะเขียนกำกับว่าแผงว่างไม่เท่ากับปกติ**
ถ้าไม่มีใครส่งข้อมูลเข้ามา แผงจะว่าง ซึ่ง**ต่างจาก "ประเมินแล้วปกติ"**
และเป็นสถานะที่ต้องรีบตรวจ หลักเดียวกับที่ `verdict` แยก `indeterminate`
ออกจาก `normal`

## ⚠️ ของที่ยังไม่ได้ทดสอบ

**แผงแนวโน้มยังว่างในการทดสอบนี้** เพราะ `TrendMonitor` ต้องมีข้อมูล
อย่างน้อย 4 วันจึงคำนวณ Mann-Kendall ได้ แต่การทดสอบกินเวลาเพียง 40 วินาที
ข้อความทั้งหมดจึงอยู่ในวันเดียวกัน ได้ `count_verdict: "too-short"`
**ซึ่งเป็นพฤติกรรมที่ถูกต้อง ไม่ใช่บั๊ก**

ถ้าจะเห็นแผงนี้ทำงานต้องใช้ `simulate.py --backfill-hours` ย้อนหลังหลายวัน
หรือรอให้ระบบเดินจริงหลายวัน

**ยังไม่ได้เปิดดูแดชบอร์ดด้วยตา** ตรวจได้ว่าไฟล์ถูก mount เข้า container แล้ว
(26,776 ไบต์ มีคำว่า Mann-Kendall) และ log บอกว่า `finished to provision
dashboards` โดยไม่มี error แต่ยังไม่ได้เปิดหน้าเว็บดูว่าแผงวาดออกมาหน้าตาดีไหม

> 🚩 **หมายเหตุ** ระหว่างทดสอบผมเรียก API ของ Grafana ด้วยรหัส `admin:admin`
> ซึ่งผิด (รหัสจริงอยู่ใน `stack/.env`) หลายครั้งติดกันจน Grafana บล็อก
> การล็อกอินชั่วคราวตามกลไกป้องกัน brute-force **เป็นการบล็อกชั่วคราว
> หายเองใน 5–10 นาที ไม่ต้องแก้อะไร** และไม่กระทบข้อมูลหรือแดชบอร์ด
> บทเรียนคือ**อ่านรหัสจาก `.env` ก่อนเสมอ อย่าเดา**
