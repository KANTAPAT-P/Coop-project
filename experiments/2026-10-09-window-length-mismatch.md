## 2. วิธีวัด

### ข้อมูล

ไฟล์ `normal` **29 ไฟล์ ชุดเดียวกับที่เทรนเส้นฐาน** (เลือกด้วยเกณฑ์เดียวกับ
`eval_detector.py` คือ `rot_hz` ใน 13.1–61.2 Hz แล้วเอา 3 ใน 5 ตามอันดับความเร็ว)
× 6 ช่องสั่นสะเทือน × 11 หน้าต่างย่อยต่อไฟล์ = **1,914 หน้าต่าง**

#### ⚠️ วัดได้ 66 ตัวชี้วัด ไม่ใช่ 72 ตัวของโมเดล

`channel_features()` คืน 11 ตัว × 6 ช่อง = **66 ตัว** ส่วน `p2p` อีก 6 ตัว
`feature_grid.py` คำนวณแยกเอง จึงไม่ได้วัดในรอบนี้

`p2p` ใช้มัธยฐานของหน้าต่างย่อย **67 ms** ซึ่งซ้อนอยู่ในหน้าต่างใหญ่
ในหน้าต่าง 410 ms ตัดได้ 6 ชิ้น เทียบกับ 72 ชิ้นในไฟล์เต็ม
→ คาดว่า **bias ต่ำแต่ความแปรปรวนสูงขึ้น** เพราะมัธยฐานของ 6 ค่าแกว่งกว่า
มัธยฐานของ 72 ค่า **แต่ยังไม่ได้วัด ห้ามเขียนในรายงานว่าวัดแล้ว**

ดังนั้นตัวเลข "11 ตัวติดเกณฑ์" เป็น **ขอบล่าง** ของจำนวนจริง

### คุมตัวแปรให้เหลือตัวเดียว

**ตรึง fs ไว้ที่ 51,200 Hz ทั้งสองฝั่ง** เปลี่ยนเฉพาะ `n`
หน้าต่าง 410 ms ที่ 51,200 Hz = 20,972 ตัวอย่าง

ถ้าเปลี่ยน fs ไปเป็น 20,000 ด้วย จะมีสองตัวแปรเปลี่ยนพร้อมกันแล้วแยกไม่ออกว่า
ส่วนต่างที่เห็นมาจากอะไร (เรื่อง fs เป็นปัญหาแยกอีกข้อ ดูหัวข้อ 6)

### วัดสองแบบ เพื่อแยกบั๊กออกจากฟิสิกส์

`channel_features()` รับพารามิเตอร์ `tol_hz` = ความกว้างหน้าต่างค้นพีค 1×/2×
ค่าเริ่มต้น `None` แปลเป็น 2% ของความเร็วรอบ ซึ่งที่ 30 Hz คือ ±0.6 Hz
**แคบกว่าหนึ่งช่องความถี่ของหน้าต่าง 410 ms (2.44 Hz)**

| โหมด | `tol_hz` | แทนอะไร |
|---|---|---|
| `naive` | ไม่ส่ง (ใช้ค่าเริ่มต้น) | สิ่งที่จะเกิดถ้าย้ายโค้ดไป ESP32 ตรงๆ |
| `fixed` | 3 ช่องความถี่ = 7.32 Hz | ทำตามที่ docstring บอกไว้แล้ว |

**ส่วนต่างระหว่างสองโหมด = ขนาดของบั๊ก · ที่เหลือใน `fixed` = ผลของความยาวจริงๆ**

## 4. ทำไม `env_floor` ถึงพุ่ง 272% — อธิบายได้ด้วยเลขคณิต

`env_floor` = **มัธยฐานของ envelope spectrum ในย่าน 2–250 Hz** คือ "พื้น" ไม่ใช่พีค

สูตรสเปกตรัมใน `src/features/spectral.py:45` หารด้วย `N`

```python
mag = np.abs(np.fft.rfft(x * w)) * 2.0 / (len(x) * gain)
```

การหารด้วย `N` ทำให้ **แอมพลิจูดของคลื่นไซน์** คงที่ไม่ว่าหน้าต่างยาวแค่ไหน
ซึ่งเป็นสิ่งที่ต้องการ **แต่สำหรับสัญญาณรบกวนมันไม่คงที่** เพราะพลังงานของ noise
กระจายทั่วทุกช่อง ยิ่งหน้าต่างยาว ยิ่งมีช่องเยอะ แต่ละช่องยิ่งได้ส่วนแบ่งน้อยลง

```
ความสูงของพื้น  ∝  1/√N
```

### ตรวจกฎนี้กับ white noise สังเคราะห์

| N | ช่องในย่าน 2–250 Hz | มัธยฐาน | เทียบ |
|---:|---:|---:|---:|
| 250,000 | 1,211 | 4.02e-03 | 1.00× |
| 20,992 | 102 | 1.56e-02 | **3.89×** |
| 8,192 | 40 | 2.20e-02 | 5.46× |

### เทียบสามทาง

| ที่มา | อัตราส่วน | เป็น % |
|---|---:|---:|
| ทฤษฎี `√(250000/20972)` | 3.45× | +245% |
| white noise สังเคราะห์ | 3.89× | +289% |
| **ข้อมูล MAFAULDA จริง** | **3.72×** | **+272%** |

ข้อมูลจริงอยู่ระหว่างทฤษฎีกับ white noise ซึ่งสมเหตุสมผล เพราะ envelope
ของสัญญาณจริงไม่ใช่ noise บริสุทธิ์ มีโครงสร้างอยู่บ้าง

> **ค่าที่เปลี่ยนไปไม่ได้มาจากเครื่องจักร เครื่องเดียวกันทุกประการ แต่หน่วยวัดเปลี่ยน**
> เหมือนเทรนโมเดลด้วยเซนติเมตรแล้วเอาไปใช้กับข้อมูลหน่วยนิ้ว

### ⚠️ `env_rel` ถูกออกแบบให้ไม่ขึ้นกับสเกล แต่ก็ยังพัง

คอมเมนต์ใน `screen_signatures.py:116` เขียนว่า `env_rel = env_floor / band_rms`
มีไว้เพื่อ **"ไม่ขึ้นกับความไวเซ็นเซอร์"** ซึ่งถูกต้องตามที่ตั้งใจ
แต่ `band_rms` แทบไม่ขยับเมื่อหน้าต่างสั้นลง (เหมือน `rms` ที่ +2.1%)
ขณะที่ตัวเศษพุ่ง 272% → **`env_rel` จึงพุ่งตามไปทั้งก้อน** และได้ `z` แย่ที่สุดในชุด

> **การ normalize กำจัดตัวแปรรบกวนได้ทีละตัว ไม่ใช่ทั้งหมด**
> `env_rel` ภูมิคุ้มกันความไวเซ็นเซอร์ แต่ไม่ภูมิคุ้มกันความยาวหน้าต่าง
> ชื่อที่มีคำว่า "rel" หรือ "ratio" ชวนให้เชื่อว่ามันไม่ขึ้นกับอะไรเลย ซึ่งไม่จริง

## 6. ปัญหาแยกอีกข้อที่เจอตอนไล่โค้ด — `fs` ถูกตรึงไว้

```python
# src/features/screen_signatures.py:47
FS = sampling_rate()                 # = 51,200 จาก config.yaml
...
f, m = spectral.spectrum(x, FS)      # ใช้ค่าคงที่ระดับโมดูล ไม่ใช่พารามิเตอร์
```

`channel_features()` **ไม่รับ `fs` เป็นพารามิเตอร์** ถ้าป้อนข้อมูล 20 kHz จาก ESP32
เข้าไป **แกนความถี่จะผิดไป 2.56 เท่า โดยไม่มี error ใดๆ**

เป็นกับดักพันธุ์เดียวกับเรื่อง 50 kHz vs 51.2 kHz เป๊ะๆ คือ **ค่าคงที่ที่ผิด
ไม่ทำให้โปรแกรมพัง มันทำให้ผลผิดอย่างเงียบๆ**

ต้องแก้ให้ `fs` เป็นพารามิเตอร์ก่อนขึ้น ESP32

### ของแถมจากการเทรนใหม่ และกับดักของมัน

ซึ่งเยอะกว่าเดิม 11 เท่า และเป็นสิ่งที่เราขาดมาตลอด (ดูหัวข้อ
"ไฟล์ปกติ 29 ไฟล์ตั้งเกณฑ์สำหรับคาบส่ง 10 วินาทีไม่ได้" ใน `CLAUDE.md`)

🚨 **แต่ห้ามนับ 319 เป็นจำนวนตัวอย่างอิสระ** ชิ้นที่ติดกันจากไฟล์เดียวกันคือ
window ที่ติดกัน ซึ่งคือ leakage ตัวเดียวกับที่วัดไว้ว่ากินไป 27 จุด accuracy
(`experiments/2026-09-25-split-leakage.md`)

ค่า `cv ใน/ข้าม` ในตารางหัวข้อ 3 เป็นหลักฐานเชิงปริมาณของข้อนี้ ทุก feature

ความต่างระหว่างไฟล์ **2–25 เท่า** → แทบไม่มีข้อมูลใหม่

## 8. สิ่งที่ต้องทำต่อ

- [ ] แก้ `channel_features()` ให้รับ `fs` เป็นพารามิเตอร์
- [ ] เพิ่มตัวเลือก `--window-ms` ให้ `feature_grid.py` แล้วสร้างตารางใหม่ที่ 410 ms
- [ ] เทรนเส้นฐานใหม่ด้วย `eval_detector.py` บนตารางนั้น
- [ ] บันทึก `window` ที่ใช้เทรนลงในไฟล์โมเดล แล้วให้ `ingest.py` **ปฏิเสธข้อความ
      ที่ `window` ไม่ตรงกับที่เทรน** → ตอบ `indeterminate` ไม่ใช่ประเมินต่อ
- [ ] วัด recall ใหม่ทั้งชุด เพราะเกณฑ์เปลี่ยนหมด
- [ ] วัด `p2p` ด้วย ซึ่งรอบนี้ยังไม่ได้วัด (ดูหมายเหตุในหัวข้อ 2)

ข้อที่สี่สำคัญที่สุด **มันเปลี่ยนความผิดพลาดเงียบๆ ให้เป็นความผิดพลาดที่ส่งเสียง**
ฟิลด์ `window` อยู่ใน JSON มาตั้งแต่ §4.1 แล้ว แต่ **ไม่มีใครอ่านมัน**
ฟิลด์ที่ไม่มีใครตรวจก็เหมือนไม่มี
