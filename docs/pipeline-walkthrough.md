## ① สัญญาณดิบ — ปริมาณที่เป็นเหตุผลของทั้งโปรเจกต์

### เข้า → ออก

| | |
|---|---|
| **เข้า** | แรงสั่นสะเทือนทางกายภาพที่ผิวเครื่องจักร |
| **ออก** | อาร์เรย์ตัวเลข 250,000 × 8 (หนึ่งไฟล์ MAFAULDA) |
| **โค้ด** | [src/data/mafaulda.py](../src/data/mafaulda.py) ฟังก์ชัน `load()` |

### ทำอะไรทีละขั้น

1. **accelerometer แปลงความเร่งเป็นแรงดัน** IMI 601A01 (แกนเดี่ยว) 3 ตัว
   และ IMI 604B31 (สามแกน) 1 ตัว ความไว 100 mV/g เท่ากันทุกตัว
2. **NI 9234 สองโมดูลแปลงเป็นดิจิทัล** ที่ 51,200 Hz ช่องละ 4 ช่อง = 8 ช่อง
3. **บันทึกลง CSV ไม่มี header** → ต้องอ่านด้วย `pd.read_csv(path, header=None)` **เสมอ**
4. **เรียงคอลัมน์ตามนี้ตายตัว** `tach · u_axial · u_radial · u_tang ·
   o_axial · o_radial · o_tang · mic`

### ตัวเลขที่วัดได้

| | ค่า |
|---|---:|
| อัตราสุ่ม | **51,200 Hz** |
| ช่องสัญญาณ | 8 = tachometer + สั่นสะเทือน 6 + ไมโครโฟน |
| หนึ่งไฟล์ MAFAULDA | 250,000 แถว = **4.8828 วินาที** |
| ขนาดเป็น float64 | 16.0 MB |
| ขนาดไฟล์ CSV จริงบนดิสก์ | 17.6 MB |
| **อัตราข้อมูลดิบ** | **3,277 kB/s ต่อเครื่อง** |
| ชุดข้อมูลทั้งหมด | 1,951 ไฟล์ · 31 GB หลังแตก |

**3,277 kB/s × 6 เครื่อง = 19.7 MB/s ตลอด 24 ชั่วโมง** ส่งขึ้น cloud ไม่ได้
ทั้งเชิงแบนด์วิดท์และค่าใช้จ่าย **นี่คือเหตุผลทั้งหมดที่ระบบต้องประมวลผลที่ edge**

### 🚨 กับดักข้อแรกของทุกคน — อัตราสุ่มที่เอกสารต้นทางบอกผิด

เอกสาร MAFAULDA เขียนว่า 50,000 Hz ซึ่งคลาด 2.4% พิสูจน์แล้วสองชั้นว่า
**sampling rate จริงคือ 51,200 Hz** (`experiments/2026-10-02-sampling-rate-filename-proof.md`)

**หลักฐานที่แข็งที่สุด ไม่อ่านข้อมูลแม้แต่แถวเดียว** ชื่อไฟล์ทุกชื่อเป็น
จำนวนเต็มเท่าของ `fs/250000` พอดี

| fs ที่สมมติ | ความละเอียด FFT | ชื่อไฟล์ที่ลงตัวพอดี |
|---:|---:|---|
| **51,200 Hz** | 0.2048 Hz | **246 / 246 = 100.00%** ✅ |
| 50,000 Hz | 0.2000 Hz | 2 / 246 = 0.81% ❌ |

**ถ้าใช้ค่าผิด แกนความถี่ของกราฟทุกใบจะคลาด 2.4%** ที่ 30 Hz คิดเป็น 2 Hz
ที่ตำแหน่ง BPFO ซึ่งเทียบกับความละเอียด 0.2048 Hz แล้วคือผิดไป 10 ช่องความถี่
→ **อ่าน `fs` จาก `config.yaml` ผ่าน `src.paths.sampling_rate()` เสมอ ห้าม hardcode**

### 🚨 กับดักที่สอง — ช่องสัญญาณไม่ได้เท่าเทียมกัน

| ช่อง | ปัญหา | ขนาด |
|---|---|---|
| `o_radial` | สัญญาณอ่อนผิดปกติทุกคลาส | **0.050–0.498 เท่า** ของช่องอื่น |
| `mic` | สเกลพุ่งสูงเฉพาะ 83 จาก 333 ไฟล์ของคลาส imbalance | **~150 เท่า ใน 25% ของไฟล์** |

สาเหตุของทั้งสองข้อ**ยังไม่ทราบ** และ `o_radial` ยังมีอาการที่อธิบายไม่ได้อีกชั้น
คือที่คลาส `underhang` ค่าพุ่งขึ้นเกือบ 10 เท่าของคลาสอื่น แปลว่า
**ทิศทางการสั่นของความเสียหายแต่ละชนิดมีผลด้วย ไม่ใช่แค่คุณสมบัติของช่อง**

→ **ห้ามเทียบค่าดิบ underhang กับ overhang ตรงๆ** ต้อง normalize ก่อน

## ② ความเร็วรอบ — ตัวแปรที่คุมความถูกต้องของทุกอย่างที่เหลือ

### เข้า → ออก

| | |
|---|---|
| **เข้า** | ช่อง `tach` (พัลส์จากแถบสะท้อนแสงบนเพลา) 20,972 ค่า |
| **ออก** | `rot_hz` หนึ่งค่า + `rot_quality` หนึ่งใน `ok/noisy/lost/stopped` |
| **โค้ด** | [src/data/tachometer.py](../src/data/tachometer.py) · ตรวจด้วย `validate_tachometer.py` |

### ทำอะไรทีละขั้น

1. **หา threshold สองระดับ** (Schmitt trigger) เพื่อไม่ให้ขอบเดียวถูกนับซ้ำ —
   จุดกึ่งกลางเป็น**ค่าคงที่** `DEFAULT_THRESHOLD = 2.5` ส่วนระยะห่างของสองระดับ
   คิดเป็น 15% ของช่วงเปอร์เซ็นไทล์ 5–95 ซึ่งคำนวณจากสัญญาณ
   ⬜ โหมด `threshold=None` ที่คำนวณจุดกึ่งกลางเองมีอยู่แล้ว **แต่ยังไม่มีผู้เรียกใดใช้**
2. **หาขอบขาขึ้น** คือจุดที่สัญญาณข้าม threshold จากล่างขึ้นบน
3. **ทิ้งขอบที่อยู่ใกล้ขอบก่อนหน้าเกินไป** (refractory period) ระยะขั้นต่ำมาจาก
   **ขีดจำกัดเชิงฟิสิกส์** คือเพลาหมุนไม่เกิน 70 Hz ไม่ได้มาจากตัวข้อมูลเอง
4. **นับจำนวนรอบจากปลายถึงปลาย** แล้วหารด้วยเวลาที่ใช้

```python
revs = np.maximum(np.round(np.diff(edges) / np.median(np.diff(edges))), 1)
rot_hz = fs * revs.sum() / (edges[-1] - edges[0])
```

ความคลาดของตำแหน่งขอบแต่ละอันหักล้างกันเองเมื่อวัดจากปลายถึงปลาย เหลือเพียง
ความคลาดของขอบแรกกับขอบสุดท้าย ส่วนการปัดเป็นจำนวนรอบทำให้ทนต่อพัลส์ที่หายไป

### ตัวเลขที่วัดได้

| | ค่า |
|---|---:|
| ผ่านเกณฑ์ ±1% | **49 จาก 49 ไฟล์** |
| ช่วงอัตราส่วนต่อชื่อไฟล์ | 0.99704–1.00738 |
| มัธยฐาน | **1.00062** |
| jitter | 0.209% |
| ช่วงความเร็วในชุดข้อมูล | 12.288–61.44 Hz (737–3,686 rpm) |

**ชื่อไฟล์คือ ground truth** เช่น `28.8768.csv` คือ 28.8768 Hz
การมีค่าอ้างอิงให้ตรวจสอบคือสิ่งเดียวที่ทำให้จับได้ว่า `fs` ผิด

### ทำไมขั้นนี้ไม่ใช่แค่ขั้นเตรียมข้อมูล

**เส้นฐานของตัวชี้วัดทั้ง 72 ตัวเป็นฟังก์ชันของ `rot_hz`** เพราะวัดในคลาส `normal`
เองแล้วพบว่า **34 ตัวมีสหสัมพันธ์กับความเร็วรอบเกิน 0.7** (สูงสุด
`u_axial.e_mid` ที่ 0.98) ถ้าตั้งเกณฑ์เป็นค่าคงที่ตัวเดียว ระบบจะเตือนทุกครั้ง
ที่เครื่องเร่งรอบ

→ **ถ้าวัดความเร็วไม่ได้ ระบบต้องตอบ `indeterminate` ไม่ใช่ประเมินต่อ** (ดูขั้น ⑥)

> **เมื่อ normalize ด้วยตัวแปรใด ความน่าเชื่อถือของตัวแปรนั้นคุมทั้งระบบ**

### 🚨 สามกับดักของ tachometer ที่เสียเวลาไปมาก

| # | กับดัก | ผิดไปเท่าไร |

## ③ สกัด feature — จุดที่ข้อมูลหดลงมากที่สุด

### เข้า → ออก

| | |
|---|---|
| **เข้า** | 20,972 × 6 ช่องสั่นสะเทือน = 125,832 ตัวเลข + `rot_hz` |
| **ออก** | **72 ตัวเลข** |
| **โค้ด** | [src/features/screen_signatures.py](../src/features/screen_signatures.py) `channel_features()` · [src/features/feature_grid.py](../src/features/feature_grid.py) |

### ทำอะไรทีละขั้น — ต่อหนึ่งช่องสัญญาณ

1. **ลบค่าเฉลี่ย** แล้ว **กรองความถี่ต่ำกว่า 10 Hz ทิ้ง** (butterworth order 4,
   zero-phase) เพื่อกัน drift ของเซ็นเซอร์
   ⚠️ ที่ความเร็วต่ำกว่า ~15 Hz ฟิลเตอร์เริ่มกินพีค 1× ไปบ้าง
2. **คำนวณสถิติในโดเมนเวลา** `rms` `kurt` `crest`
3. **คำนวณสเปกตรัม** FFT พร้อมหน้าต่าง Hann และชดเชย gain ของหน้าต่าง
4. **หาพีคที่ 1× และ 2×** ของความเร็วรอบ ในหน้าต่างค้นกว้าง
   `max(2% ของ rot_hz, 2 ช่องความถี่)` → ได้ `h1_frac` และ `r21`
5. **รวมพลังงานสามย่าน** `e_low` (5 Hz ถึง 10× rot) · `e_mid` (10× rot ถึง 2 kHz) ·
   `e_high` (2–10 kHz) แล้วหารด้วยพลังงานรวม
6. **ทำ envelope analysis** bandpass 2–5 kHz → Hilbert → FFT ของ envelope
   → `kurt_band` `env_floor` `env_rel`
7. **คำนวณ `p2p`** แยก โดยตัดหน้าต่างย่อย 67 ms แล้วหามัธยฐานของ peak-to-peak

### 12 ตัวชี้วัดแบ่งเป็น 5 กลุ่ม

| กลุ่ม | feature | วัดอะไร | ไวต่ออะไร |
|---|---|---|---|
| ขอบเขต | `p2p` `rms` | ระดับความแรงรวม | ความไวเซ็นเซอร์ ⚠️ |
| รูปร่างในเวลา | `kurt` `crest` | ความแหลม / การกระแทก | ไม่ขึ้นกับสเกล ✅ |
| สเปกตรัม | `h1_frac` `r21` | สัดส่วนพลังงานที่ 1× และอัตราส่วน 2×/1× | ไม่ขึ้นกับสเกล ✅ |
| แถบพลังงาน | `e_low` `e_mid` `e_high` | รูปร่างของสเปกตรัม | ไม่ขึ้นกับสเกล ✅ |
| envelope | `kurt_band` `env_floor` `env_rel` | การกระแทกในย่าน 2–5 kHz | **ความยาวหน้าต่าง** 🔴 |

**ทุกตัวเบาพอที่จะคำนวณบนไมโครคอนโทรลเลอร์ได้** ซึ่งเป็นข้อกำหนดของสถาปัตยกรรม
เป้าหมาย นิยามและกับดักของแต่ละตัวอยู่ใน
[docs/feature-reference.md](feature-reference.md)

### ทำไมต้องมี envelope analysis แยกจาก FFT ธรรมดา

FFT ธรรมดายิงใส่สัญญาณดิบ **ไม่เห็น** ความถี่ความเสียหายของตลับลูกปืน
เพราะรอยแตกเล็กๆ ไม่ได้ทำให้เกิดการสั่นที่ความถี่ BPFO โดยตรง
มันแค่**กระแทก**ทุกครั้งที่ลูกปืนกลิ้งผ่านรอย แล้วแรงกระแทกไปกระตุ้นความถี่
ธรรมชาติของโครงสร้างที่ 2–5 kHz ให้สั่นแล้วค่อยๆ ซาลง

สิ่งที่เซ็นเซอร์เห็นจึงเป็น**คลื่น 2–5 kHz ที่ถูกมอดูเลตด้วยจังหวะกระแทกช้าๆ**
envelope analysis ดึงจังหวะนั้นออกมา

```python
def envelope_spectrum(sig, fs, lo=2000, hi=5000):
    b, a = butter(4, [lo/(fs/2), hi/(fs/2)], btype='band')
    env = np.abs(hilbert(filtfilt(b, a, sig)))
    env = env - env.mean()
    return np.fft.rfftfreq(len(env), 1/fs), np.abs(np.fft.rfft(env))
```

**imbalance อยู่ย่านต่ำ (1× รอบหมุน) ส่วน bearing fault อยู่ย่านสูง (2–5 kHz)**
— ไม่ทับกัน จึงแยกออกจากกันได้

### 🚨 กับดักที่เสียเวลาที่สุดในขั้นนี้ — QoS 1 ไม่ได้แปลว่าข้อมูลไม่หาย

ทดสอบรอบแรกส่ง 4,440 ข้อความ **ผู้รับได้เพียง 2,262 หายไป 49% โดยไม่มี error ใดๆ**
สาเหตุสองข้อซ้อนกัน

1. `client.publish()` ของ paho แค่เอาข้อความเข้าคิวแล้วคืนค่าทันที
   ถ้า `disconnect()` ก่อนคิวระบายหมด ข้อความที่เหลือหายเงียบๆ
2. Mosquitto จำกัดคิวของผู้รับไว้ที่ **1,000 ข้อความ** โดยค่าเริ่มต้น
   ส่วนเกินถูกทิ้งแม้ใช้ QoS 1

> QoS 1 รับประกันว่า *ข้อความที่ broker รับไว้แล้ว* จะถูกส่งต่ออย่างน้อยหนึ่งครั้ง
> **ไม่ได้รับประกันว่าทุกข้อความที่เราเรียก `publish()` จะไปถึง broker**

**วิธีแก้** คลาส `Publisher` นับจำนวนที่ broker ตอบรับ (callback `on_publish`)
เทียบกับที่ส่งไป แล้วหน่วงตัวเองเมื่อคิวค้างเกิน 400 และรอให้คิวระบายหมด
ก่อนตัดการเชื่อมต่อ **ต้องทำแบบเดียวกันในเฟิร์มแวร์ ESP32**

→ **บทเรียน: ต้องนับจำนวนข้อความสองฝั่งเสมอ** ระบบรายงานว่าทำงานปกติได้
ทั้งที่ข้อมูลหายไปครึ่งหนึ่ง

### Last Will and Testament — แยก "ปกติ" จาก "ตายแล้ว"

topic `status` ตั้งเป็น **retained** และเป็น **LWT** ของ client
ถ้าอุปกรณ์หลุด broker จะ publish ข้อความ `offline` ให้เอง

**ถ้าไม่ตั้ง LWT ระบบจะแยกไม่ออกระหว่าง "เครื่องจักรปกติ ไม่มีอะไรผิด"
กับ "อุปกรณ์ตายไปแล้ว ไม่มีใครวัดอยู่"** ซึ่งเป็นสองสถานการณ์ที่อันตรายต่างกันสิ้นเชิง
— เป็นปัญหาเดียวกับที่ `verdict: indeterminate` แก้ในระดับการประเมิน

### ชั้น 1 — detector · มองย้อนหลัง 1 ข้อความ

#### ทำอะไรทีละขั้น

1. **แปลงเป็น log** สำหรับตัวชี้วัดที่เป็นปริมาณบวกและกระจายแบบ skew
   (`rms` `p2p` `env_floor` …) เพื่อให้เศษเหลือใกล้สมมาตร
2. **คำนวณค่าที่คาด** จากเส้นตรงของความเร็วรอบ
3. **หาค่า z** แล้วนับว่ามีกี่ตัวที่หลุดเกณฑ์ย่อย

```
expected = a + b x rot_hz          ต่อ feature, fit จากไฟล์ normal เท่านั้น
z        = (measured - expected) / scale
```

| เกณฑ์ | ค่า | มาจากไหน |
|---|---|---|
| กฎที่เลือก | `vote` | recall สูงกว่า `max_z` ที่อัตราการเตือนผิดเท่ากัน |
| เกณฑ์ย่อยต่อตัวชี้วัด | `\|z\| > 3` | `z_feat` |
| ผิดปกติเมื่อ | **มี ≥ 9 ตัวหลุดเกณฑ์ย่อย** | `vote_min` = ค่าสูงสุดของไฟล์ปกติ (8) + 1 |
| หรือเตือนทันทีเมื่อ | `max_z > 60.2` | `hard_z` = 3 เท่าของค่าสูงสุดที่ไฟล์ปกติทำได้ |

**ค่าเหล่านี้ไม่ได้เดา ตั้งจากข้อมูลด้วย leave-one-out** คือตัดไฟล์ปกติออกทีละไฟล์
ประมาณเส้นฐานใหม่จากที่เหลือ แล้วให้คะแนนไฟล์ที่ตัดออก ทำซ้ำทุกไฟล์
→ ได้การแจกแจงของคะแนนบนข้อมูลที่โมเดล**ไม่เคยเห็น** โดย**ไม่ต้องสมมติรูปร่าง
การแจกแจงใดๆ และไม่ต้องแตะไฟล์ที่เสียเลย**

🚨 **ตัดออกทีละไฟล์ ไม่ใช่ทีละหน้าต่าง** เพราะไฟล์หนึ่งให้ 11 หน้าต่างที่คล้ายกันเอง
ถ้าตัดออกทีละหน้าต่าง โมเดลจะเห็นหน้าต่างพี่น้องอยู่ในชุดเทรน

#### ผลที่วัดได้

| | ค่า |
|---|---:|
| เทรนด้วย | ไฟล์ `normal` **29 ไฟล์** = 319 หน้าต่าง |
| วัดกับ | ไฟล์ที่เสีย **1,092 ไฟล์** = 12,012 หน้าต่าง (ไม่เคยเห็นเลย) |
| recall ต่อข้อความ | **0.872** |
| **recall ต่อเครื่อง หลังด่านยืนยันซ้ำ** | **0.856** |
| เตือนผิดบนไฟล์ปกติ | **1 จาก 47 ไฟล์** |
| **ขอบบน 95% ของอัตราต่อข้อความ** | **0.097** |
| เวลา inference ต่อข้อความ (โน้ตบุ๊ก) | **36.6 µs** |
| ⬜ เวลา inference บน Raspberry Pi 5 | **ยังไม่วัด** |

**ตัวที่แย่ที่สุดทุกตัวคือระดับความรุนแรงต่ำสุดของคลาสนั้น** ซึ่งเป็นสิ่งที่
ฟิสิกส์บอกว่าต้องเกิด ถ้าตัวเลขรวมไม่แจกแจง เลขสวยจะมาจาก ball fault ตัวเดียว

#### ✅ หลักฐานว่าโมเดลจับความเสียหายจริง ไม่ใช่ร่องรอยของรอบบันทึก

recall **ขึ้นตามความรุนแรงอย่างเป็นระบบ** ซึ่งร่องรอยการประกอบอธิบายไม่ได้
เพราะไม่มีเหตุผลใดที่ร่องรอยการประกอบจะเรียงตามความรุนแรงพอดี

| คลาส | สหสัมพันธ์อันดับ ความรุนแรง↔recall | recall ต่ำสุด → สูงสุด |
|---|---:|---|
| horizontal-misalignment | **+1.000** | 0.271 → 1.000 |
| vertical-misalignment | **+0.943** | 0.606 → 0.996 |
| imbalance | **+1.000** | 0.511 → 1.000 |

⚠️ **แต่ `overhang cage_fault` ได้ 0.782 ซึ่งยังสูงกว่าที่ควรเป็น** เพราะเราวัดเอง
ว่าคลาสนี้ไม่มีลายเซ็นใดๆ ที่หาเจอ **ยังห้ามเคลมว่าจับ cage fault ได้**

#### 🚨 สามบทเรียนที่แก้ไปแล้วในชั้นนี้

**(ก) MAD เป็นตัวประมาณการกระจายตัวที่ผิดสำหรับงานนี้**
รอบแรกใช้ MAD เพราะ "ทนค่าผิดปกติ" ได้ผลคือเตือนผิด **3,360 ครั้ง/วัน**
และเตือนผิดบนไฟล์ที่ใช้เทรนเองถึง 6 จาก 29 ไฟล์
วัดได้ว่า 6 ตัวชี้วัดมี sd ของเศษเหลือสูงกว่าค่าจาก MAD 2.1–2.7 เท่า

> **"ทนค่าผิดปกติ" เป็นคุณสมบัติที่ดีเฉพาะเมื่อมีค่าผิดปกติ
> ถ้าข้อมูลสะอาดโดยการออกแบบ มันกลายเป็นการทิ้งข้อมูลที่ต้องใช้**

**(ข) ค่าคงที่ที่เป็นเกณฑ์ตัดสิน ห้ามตั้งเดาในโค้ด**
ตั้ง `hard_z = 12.0` ไว้ในโค้ด **แต่ `max_z` ของไฟล์ปกติเองสูงถึง 12.52**
ไฟล์ปกติจึงข้ามด่านยืนยันซ้ำได้ ทำให้การรับประกันอัตราการเตือนผิดเป็นโมฆะ
**และค่านั้นเปลี่ยนตามหน้าต่างด้วย** เส้นฐานไฟล์เต็มได้ 37.6
เส้นฐาน 410 ms ที่ใช้อยู่ได้ **60.2** → อ่านจากไฟล์โมเดลเสมอ

**(ค) เห็นศูนย์เหตุการณ์ ไม่ได้แปลว่าอัตราเป็นศูนย์**
เส้นฐานรุ่นแรกไม่เตือนผิดเลยจาก 47 ไฟล์ แต่สรุปว่าอัตราเป็นศูนย์**ผิด**
สิ่งที่พูดได้คือ **อัตราไม่เกินขอบบน Clopper-Pearson ด้านเดียว 95%**
(ตรงกับกฎสามส่วน `3/n`) **ตัวเลขทุกตัวในรายงานคำนวณจากขอบบนนี้**

🚨 **ตัวส่วนต้องเป็นจำนวนไฟล์ ไม่ใช่จำนวนหน้าต่าง** ตารางหน้าต่างมีแถวมากกว่า
11 เท่าแต่ไม่ได้มีข้อมูลมากขึ้น 11 เท่า (`cv ในไฟล์ / cv ข้ามไฟล์` = 0.04–0.46)

> **leakage โผล่ในช่องของการประมาณความเชื่อมั่นได้ด้วย ไม่ใช่แค่ในช่อง accuracy
> และตรงนั้นมองเห็นยากกว่า** เพราะไม่มีตัวเลขไหนดูสูงผิดปกติ
> มีแต่ช่วงความเชื่อมั่นที่แคบเกินจริง

## ⑦ ผลลัพธ์

### `verdict` มี 4 ค่า ไม่ใช่ 2

| verdict | ความหมาย | สถานะ |
|---|---|---|
| `normal` | ตรวจแล้วไม่พบความผิดปกติ | ✅ |
| `unknown_anomaly` | ผิดปกติ แต่ไม่รู้ว่าแบบไหน | ✅ |
| `fault` | ระบุชนิดความเสียหายได้ | ⬜ **ยังไม่ได้ทำ** |
| `indeterminate` | **ตรวจไม่ได้** | ✅ |

**`unknown_anomaly` แยกจาก `fault`** เพราะหน้างานจะเจอความเสียหายที่ชุดเทรนไม่มี
(เช่น BPFI ที่ MAFAULDA ไม่มีเลย) ถ้าไม่มีช่องนี้ ระบบจะถูกบังคับให้ตอบชนิด
ที่รู้จัก**อย่างมั่นใจแต่ผิด** — แนวทางจาก Costa et al. (IEEE Access 2026)

**`indeterminate` แยกจาก `normal`** เพราะ **"ตรวจแล้วไม่พบ" กับ "ตรวจไม่ได้"
ไม่เหมือนกัน** ถ้ายุบรวมกัน ระบบจะรับประกันว่าเครื่องดีทั้งที่ไม่มีใครวัดอยู่

## ⑦ ผลลัพธ์ — `unknown_anomaly` มาจากวรรณกรรม `indeterminate` เป็นของเรา

มี 10 จาก 12 ฉบับที่ทำการจำแนก (ฉบับ 03 เป็นคณิตศาสตร์ล้วน ฉบับ 07 ทำ denoising)

| ความสามารถของผลลัพธ์ | ฉบับที่มี |
|---|---|
| ตอบเป็นคลาสที่รู้จักหนึ่งคลาส (2–9 คลาส) **โดยไม่มีช่องปฏิเสธ** | **9 / 10** |
| **มีช่อง "ผิดปกติแต่ไม่รู้ว่าอะไร"** | **1 / 10** (02 Costa) |
| **มีช่อง "ตรวจไม่ได้"** | **0 / 10** |

**จำนวนคลาสที่แต่ละฉบับตอบ** 12 Ullah 2 คลาส · 08 Sanami 3 · 01/02/05 6 คลาส ·
10 Kim 7 · 06 Ūselis 9

🚩 **9 จาก 10 ฉบับถูกบังคับให้ตอบคลาสใดคลาสหนึ่งเสมอ** ซึ่งเป็นปัญหาที่
ฉบับ 02 ระบุไว้ตรงๆ ว่า classifier แบบนี้**เมื่อเจอความเสียหายชนิดที่ไม่เคยเห็น
ตอนเทรน มันจะตอบผิดอย่างมั่นใจ**

ฉบับ 02 แก้ปัญหา **classifier ที่เจอความเสียหายชนิดใหม่แล้วตอบผิดอย่างมั่นใจ**
ด้วย confidence routing ที่ τ* = 0.75 → เราเอาแนวคิดนี้มาเป็น `unknown_anomaly`

**แต่ `indeterminate` ไม่มีในฉบับใดเลย** เพราะงานออฟไลน์ไม่เคยเจอสถานการณ์
"เครื่องหยุด" หรือ "tachometer หลุด" — ข้อมูลในไฟล์สมบูรณ์เสมอ

→ **นี่คือช่องว่างที่โผล่มาเฉพาะเมื่อลงมือสร้างระบบจริง**

### explainability — เราไปไกลกว่าทุกฉบับ

| ฉบับ | ทำอะไร |
|---|---|
| 02 Costa | **อ้าง**เหตุผล feature importance ของ RF **สองครั้ง** แต่ค้นทั้ง 16 หน้าแล้ว**ไม่มีค่า importance แม้แต่ตัวเดียว** |
| 04 Bingamil | ใช้ **Relief feature selection** เป็นจุดขาย แต่**ไม่เคยบอกว่าเลือกตัวไหน** |
| 06 Ūselis | ตาราง per-sensor × per-class F1 — **ใกล้ที่สุด** |
| **ของเรา** | **ส่ง `evidence` ไปกับทุกข้อความ** ว่าตัวชี้วัดไหนหลุดเกณฑ์ พร้อมค่า z |

> **ทั้งสองฉบับแรกมีเครื่องมือที่สกัดลายเซ็นได้อยู่ในมือ แต่ใช้มันเพื่อดัน
> accuracy แล้วไม่รายงานสิ่งที่เครื่องมือบอก** ซึ่งเป็นแบบแผนที่เห็นได้ทั่วไป
> ในวรรณกรรมชุดนี้

และ **ตารางลายเซ็น 8 คลาสของเรา** (`CLAUDE.md` หัวข้อ 5) ละเอียดกว่าฉบับ 06
สองระดับ

| | ฉบับ 06 | ของเรา |
|---|---|---|
| ละเอียดระดับ | ช่องเซ็นเซอร์ (6 ช่อง) | **ช่อง × ปริมาณ** (6 × 11 = 66 แบบ) |
| วัดจาก | ผลของตัวจำแนก (F1) | **ค่าที่วัดได้โดยตรง** (AUC ของ feature เดี่ยว) |

ของเขาตอบได้ว่า *"ใช้ช่อง `u_axial` แล้วตรวจ overhang ball ได้"*
ของเราตอบได้ว่า *"overhang ball ทำให้ `o_radial` ถูกครอบด้วยคลื่น ~9.93×
ความเร็วรอบ"* → **ของเราบอกกลไก ของเขาบอกแต่ผล**

### ✅ และวรรณกรรมยืนยันข้อค้นพบที่เราอธิบายไม่ได้

เราพบว่า **4 จาก 7 ลายเซ็นอยู่ที่เซ็นเซอร์ฝั่งตรงข้ามกับตลับลูกปืนที่เสีย**
และสงสัยว่าอาจเป็นร่องรอยของรอบบันทึก

**ฉบับ 06 Table II** ระบุว่า `overhang axial` ตรวจ **Underhang**-ball ได้ดีที่สุด
(F1 94.23%) และ `underhang axial` ตรวจ **Overhang**-ball ได้ F1 **100%**

→ **คนละกลุ่มวิจัย คนละวิธี เจอปรากฏการณ์เดียวกันทั้งสองทิศ และอยู่บนแกน axial
เหมือนกัน** จึงเป็นการส่งผ่านการสั่นจริง ไม่ใช่ร่องรอย

และเราวัดได้ว่า *"normal มีระดับพื้นสูงกว่าเกือบทุกคลาสที่เสีย ซึ่งผิดจาก
สัญชาตญาณ"* → **ฉบับ 06 Table III แสดงว่า Normal เป็นคลาสที่แย่ที่สุดของ
_ทุกช่อง_ ทั้ง 6 ช่อง** และต่ำถึง F1 6.25% บน overhang axial
