## 1. หลักการออกแบบ 4 ข้อ

หลักการเหล่านี้มาจากผลการทดลองในช่วงที่ 1 ไม่ใช่จากตำรา

1. **ส่งบริบทการทำงานไปพร้อมตัวชี้วัดเสมอ** — วัดได้แล้วว่าตัวชี้วัดความแรงของช่องหนึ่ง
   กระโดด 4 เท่าเมื่อความเร็วรอบผ่าน 50 Hz โดยที่ความเสียหายไม่ได้เปลี่ยน
   ถ้าไม่มีความเร็วรอบกำกับ ระบบจะแจ้งเตือนผิดทุกครั้งที่มอเตอร์เร่ง
2. **อุปกรณ์ต้องบอกได้ว่าตัวเองไม่มั่นใจ** — พบว่า 7% ของไฟล์ในชุดข้อมูลมีสัญญาณ
   tachometer เสีย ถ้าอุปกรณ์ไม่แจ้งว่าวัดความเร็วไม่ได้ ระบบปลายทางจะใช้ค่าขยะเงียบๆ
3. **ออกแบบเผื่อการเปลี่ยนแปลงตั้งแต่แรก** — ใส่หมายเลขเวอร์ชันของ schema
   และตั้งชื่อ topic ให้เพิ่มเครื่องจักรได้โดยไม่ต้องรื้อ
4. **ปกป้อง microSD** — สาเหตุการตายอันดับหนึ่งของโครงงาน IoT บน Raspberry Pi
   คือการ์ดเสื่อมจากการเขียนซ้ำ ทุกการตัดสินใจเรื่องปริมาณข้อมูลต้องคิดถึงข้อนี้

| 6 | **ส่ง `assessment` ทุกข้อความ ไม่ใช่เฉพาะตอนผิดปกติ** | ผู้ที่สมัครรับต้องแยกออกได้ระหว่าง "ประเมินแล้วปกติ" กับ "ไม่มีใครประเมินอยู่" **ถ้าส่งเฉพาะตอนผิดปกติ ความเงียบจะกำกวม** |

### 2.2 อายุของข้อมูล

```
  data age ────────────────────────────────────────────────────────►
                 now       14 days     30 days             2 years

  pdm_live        ████████████                                      10 s resolution
                      │
                      │  InfluxDB task, downsampled once per hour
                      ▼
  pdm_hourly  ⬜  ████████████████████████████████████████████      mean / min / max / count

  raw_snapshots ⬜ ████████████████████████                          files, max 10 per day

  pdm_events  ⬜  ████████████████████████████████████████████►     never deleted
```

> ⬜ **ทำแล้วเฉพาะ `pdm_live`** อีกสามอย่างยังเป็นแผน ผังนี้จึงเป็นเป้าหมาย
> ไม่ใช่สภาพปัจจุบัน **ของที่ยังไม่มีต้องกำกับไว้เสมอ** เพราะผังที่วาดของที่
> ยังไม่มีไว้เฉยๆ อันตรายกว่าผังที่ไม่มีอะไรเลย คนอ่านจะเชื่อว่ามีแล้ว

**หลักการคือข้อมูลละเอียดเก็บสั้น ข้อมูลย่อเก็บยาว**

- **14 วันแบบละเอียด** นานพอให้ย้อนดูรายละเอียดตอนเกิดการแจ้งเตือน ซึ่งเป็น
  ช่วงเวลาที่คนจะเข้าไปตรวจสอบจริง
- **2 ปีแบบรายชั่วโมง** นานพอให้เห็นแนวโน้มระยะยาวและผลของฤดูกาลหรือภาระงาน
  ที่เปลี่ยนไป โดยกินพื้นที่เพียงราว 7 เมกะไบต์ต่อปีต่อเครื่องจักร
- **สัญญาณดิบ 30 วัน** พอให้ย้อนไปสกัดตัวชี้วัดตัวใหม่ได้ถ้าเปลี่ยนวิธีวิเคราะห์
  ระหว่างทาง โดยไม่กินพื้นที่จนการ์ดเต็ม

ลูกศรจาก `pdm_live` ลง `pdm_hourly` คืองานย่อข้อมูลที่ InfluxDB จะทำเองทุกชั่วโมง
(⬜ ยังไม่ได้ตั้ง) **ข้อมูลย่อต้องถูกเขียนไว้ก่อนที่ข้อมูลละเอียดจะถูกลบเสมอ**
จึงจะไม่มีช่วงเวลาใดที่ข้อมูลหาย

## 3. 🚩 การตัดสินใจที่ 1 — โครงสร้าง MQTT topic

### 3.1 รูปแบบที่เลือก

```
pdm/<site>/<area>/<machine>/<sensor>/<kind>
```

| ระดับ | ความหมาย | ตัวอย่าง |
|---|---|---|
| `pdm` | คำนำหน้าคงที่ของโครงงานนี้ | `pdm` |
| `<site>` | โรงงานหรือสถานที่ | `plant1` |
| `<area>` | พื้นที่หรือสายการผลิต | `press-line` |
| `<machine>` | เครื่องจักร | `motor-03` |
| `<sensor>` | ชุดเซ็นเซอร์ที่ติดกับเครื่องนั้น | `acc-01` |
| `<kind>` | ชนิดข้อความ | `feature` · `status` · `raw` · `assessment` |

**ตัวอย่างจริง**

```
pdm/plant1/press-line/motor-03/acc-01/feature
pdm/plant1/press-line/motor-03/acc-01/status
pdm/plant1/press-line/motor-03/acc-01/raw
pdm/plant1/press-line/motor-03/assessment
```

### 3.2 กฎการตั้งชื่อ

- ใช้ได้เฉพาะ **a–z, 0–9 และขีดกลาง** ห้ามเว้นวรรค ห้ามอักษรไทย ห้ามตัวพิมพ์ใหญ่
- ห้ามใช้ `+` และ `#` ในชื่อ เพราะเป็นอักขระ wildcard ของ MQTT
- **ความลึกต้องคงที่ภายในชนิดข้อความเดียวกัน** เช่น `feature` ของทุกเครื่องต้องลึก
  6 ระดับเท่ากันหมด มิฉะนั้นการ subscribe ด้วย wildcard จะได้ผลไม่ตรงกัน
  เครื่องที่ไม่มีพื้นที่ย่อยให้ใส่ `main`
  **แต่คนละชนิดมีความลึกต่างกันได้** และในระบบนี้ต่างกันจริง คือ `assessment` มี 5 ระดับ
  เพราะการแจ้งเตือนเป็นเรื่องของเครื่องจักรทั้งเครื่อง ไม่ใช่ของเซ็นเซอร์ตัวใดตัวหนึ่ง
  ถ้าบังคับให้ลงลึกถึงเซ็นเซอร์จะต้องเลือกมาหนึ่งตัวแบบไม่มีเหตุผลรองรับ
- **ห้ามใส่ค่าที่เปลี่ยนบ่อยลงใน topic** เช่นความเร็วรอบหรือสถานะ
  ค่าพวกนี้ต้องอยู่ใน payload เท่านั้น มิฉะนั้นจำนวน topic จะระเบิด

### 3.3 รูปแบบการ subscribe ที่ใช้บ่อย

| ต้องการ | topic ที่ subscribe |
|---|---|
| ตัวชี้วัดจากทุกเครื่องจักร | `pdm/+/+/+/+/feature` |
| ทุกอย่างในสายการผลิตหนึ่ง | `pdm/plant1/press-line/#` |
| ผลการประเมินทั้งหมด | `pdm/+/+/+/assessment` |
| สถานะออนไลน์ของทุกอุปกรณ์ | `pdm/+/+/+/+/status` |

### 3.4 ระดับการรับประกันการส่ง (QoS) และ retained

| ชนิดข้อความ | QoS | retained | เหตุผล |
|---|---|---|---|
| `feature` | **1** | ไม่ | ต้องถึงปลายทางเพื่อไม่ให้กราฟแนวโน้มขาดช่วง แต่ไม่ต้องถึง QoS 2 ที่แพงกว่า ผู้รับกันข้อความซ้ำด้วย timestamp |
| `status` | **1** | **ใช่** | ผู้ subscribe ใหม่ต้องรู้สถานะปัจจุบันทันทีโดยไม่ต้องรอข้อความถัดไป |
| `assessment` | **1** | ไม่ | ห้ามหาย |
| `raw` | **1** | ไม่ | ก้อนใหญ่ ส่งเฉพาะตอนจำเป็น ⬜ **ยังไม่ได้ทำ** |

🚩 **"ตอนจำเป็น" ยังไม่มีกลไก และทั้งเส้นทางยังไม่มีสักชิ้น**
บรรทัด `raw` ข้างบนไม่เคยระบุว่า**ใครเป็นคนตัดสิน**ว่าจำเป็น และอุปกรณ์
ตัดสินเองไม่ได้ เพราะเส้นฐานของตัวชี้วัดทั้ง 72 ตัวอยู่ในไฟล์โมเดลบน
Raspberry Pi ไม่ได้อยู่บนอุปกรณ์ กว่าผลการประเมินจะกลับมา หน้าต่างนั้น
ก็ถูกเขียนทับไปแล้ว

`raw` กับกล่อง `raw_snapshots/` ในผัง §2.1 คือ**ปลายคนละข้างของเส้นทางเดียวกัน**
และว่างทั้งห้าชิ้น คือกลไกตัดสิน · ฝั่งอุปกรณ์ส่ง · **ฝั่งบริการรับ ซึ่ง
`ingest.py` ไม่ได้ subscribe `raw` ด้วยซ้ำ** · โค้ดเขียนไฟล์ · และนโยบายลบของเก่า

**ทางเลือกสามแบบพร้อมข้อแลกเปลี่ยน บันทึกไว้ใน `CLAUDE.md` หัวข้อ 7
ที่ Checkpoint 4** ยังไม่ได้เลือก และแบบที่ดูดีที่สุดต้องเพิ่ม topic ขาลง
ซึ่งตอนนี้ยังไม่มีเลย

### 3.5 ⚠️ Last Will and Testament — จุดที่มักถูกมองข้าม

ESP32 ต้องตั้ง **Last Will and Testament (LWT)** ไว้ที่ topic `status` ตอนเชื่อมต่อ
เพื่อให้ broker ประกาศแทนเมื่ออุปกรณ์หลุดการเชื่อมต่อแบบไม่ได้บอกลา

```
topic:    pdm/plant1/press-line/motor-03/acc-01/status
payload:  {"schema":1,"state":"offline","reason":"lwt"}
retained: true
```

**ถ้าไม่ตั้ง LWT ระบบจะแยกไม่ออกระหว่าง "เครื่องจักรปกติ ไม่มีอะไรผิด" กับ
"อุปกรณ์ตายไปแล้ว ไม่มีใครวัดอยู่"** ซึ่งเป็นสองสถานการณ์ที่อันตรายต่างกันสิ้นเชิง

### 4.2 เหตุผลของแต่ละส่วน

| ฟิลด์ | เหตุผลที่ต้องมี |
|---|---|
| `schema` | หมายเลขเวอร์ชันของโครงสร้าง ทำให้เพิ่มหรือแก้ฟิลด์ภายหลังได้โดยที่ผู้รับเวอร์ชันเก่าไม่พัง |
| `device_id` | ระบุอุปกรณ์ที่ส่ง แยกจาก topic เพราะถ้าย้ายอุปกรณ์ไปเครื่องจักรอื่นจะยังตามรอยได้ |
| `ts` | เวลาตาม **UTC รูปแบบ ISO 8601** ห้ามใช้เวลาท้องถิ่นเพราะจะสับสนตอนเทียบข้ามอุปกรณ์ |
| `window` | ความถี่การสุ่มและจำนวนตัวอย่างที่ใช้คำนวณ **จำเป็นต่อการตีความตัวชี้วัด** ความละเอียดความถี่เท่ากับ `fs/n` ถ้าไม่รู้ค่านี้จะอ่าน `h1_frac` และ `r21` ไม่ได้ ✅ **`ingest.py` ปฏิเสธข้อความที่ค่านี้ไม่ตรงกับที่โมเดลเทรน ดู §4.2.1** |
| `context` | บริบทการทำงาน ดูหลักการข้อ 1 |
| `features` | ตัวชี้วัด ใช้ชื่อแบบ `<ช่อง>.<ตัวชี้วัด>` ให้ตรงกับที่ใช้ในโค้ดวิเคราะห์อยู่แล้ว |
| `quality` | ตัวบอกว่าเชื่อข้อมูลนี้ได้แค่ไหน ดูหลักการข้อ 2 |

### 4.2.1 ✅ ฟิลด์ `window` — เคยไม่ตรงกับที่เทรน แก้แล้ว 2026-10-09

**หน้าต่างที่เทรน 410 ms** = 20,972 ตัวอย่าง @ 51,200 Hz · ความละเอียด 2.44 Hz
เก็บในฟิลด์ `window` ของ `models/baseline-normal.json`
และ `ingest.py` ปฏิเสธข้อความที่ไม่ตรง (ดูด่านที่ 2 ในผัง §2.1)

#### เรื่องที่เกิดขึ้น

ค่าที่เขียนไว้ใน §4.1 ถูกเลือกจากข้อจำกัดแรมและเวลา FFT ของ ESP32
**แต่โมเดลตอนนั้นถูกเทรนด้วยไฟล์เต็ม ซึ่งเป็นหน้าต่างอีกขนาดหนึ่ง**

| | ไฟล์ MAFAULDA ทั้งไฟล์ | ที่ออกแบบไว้ที่นี่ |
|---|---:|---:|
| แหล่ง | `src/features/feature_grid.py` | §4.1 ของเอกสารนี้ |
| fs × n | 51,200 Hz × 250,000 | 20,000 Hz × 8,192 |
| **ความยาว** | **4,883 ms** | **410 ms** |
| ความละเอียดความถี่ | 0.2048 Hz | 2.44 Hz |

ต่างกัน **11.92 เท่า** วัดผลแล้วว่าถ้าป้อนค่าจากหน้าต่าง 410 ms ของเครื่อง
**ปกติ** เข้าโมเดลตอนนั้น จะมี **11 ตัวชี้วัดติดเกณฑ์ `|z| > 3`**
(จาก 66 ตัวที่วัดได้ ซึ่งไม่ครบ 72 ตัวของโมเดล เพราะ `p2p` ยังไม่ได้วัด)
ซึ่งพอดีกับ `vote_min` เดิม และ **6 ตัวทะลุ `hard_z` เดิม 37.6**
จนข้ามด่านยืนยันซ้ำ → **เครื่องปกติจะถูกเตือนทุกข้อความ**

สาเหตุแคบมาก ทั้ง 11 ตัวเป็น `env_floor` หรือ `env_rel` ทั้งหมด เพราะทั้งสองวัด
"พื้น" ของสเปกตรัม ซึ่งสูงขึ้นตาม `1/√N` เมื่อหน้าต่างสั้นลง
ส่วน `rms` `kurt` `e_*` `kurt_band` เพี้ยนไม่เกิน 2.1%

#### ราคาที่จ่ายเมื่อเทรนใหม่บนหน้าต่างสั้น

| | ไฟล์เต็ม 4,883 ms | **หน้าต่าง 410 ms** |
|---|---:|---:|
| `vote_min` | 11 | **9** |
| `hard_z` | 37.6 | **60.2** |
| recall ต่อข้อความ | 0.913 | **0.872** |
| ขอบบน 95% ของอัตราเตือนผิด | 0.062 | **0.097** |
| ด่านยืนยันซ้ำที่ต้องใช้ | 4 ใน 5 | **5 ใน 6** |
| เตือนผิดต่อวัน | 0.60 | **0.41** |

#### ⬜ ส่วนที่ยังไม่ตรง — `fs`

โมเดลเทรนที่ **51,200 Hz** ไม่ใช่ 20,000 Hz ที่ ESP32 จะใช้ เพราะข้อมูลที่มี
บันทึกมาที่ 51,200 Hz จะเทรนที่ 20,000 ต้อง decimate ก่อน
(`resample_poly(up=25, down=64)` ให้ 20,000 Hz พอดี)

**ตอนนี้ด่านตรวจจะปฏิเสธข้อความ 20 kHz ตรงๆ** ซึ่งเป็นพฤติกรรมที่ถูกต้อง
สำหรับสิ่งที่ยังไม่ได้ยืนยัน ดีกว่าประเมินต่อแบบผิดๆ

#### ⚠️ ข้อจำกัดของด่านนี้

**ด่านเทียบแค่สิ่งที่ข้อความ *ประกาศ* ไม่ได้วัดจากค่าจริง**
อุปกรณ์ที่ประกาศหน้าต่างผิดจะผ่านด่านไปได้ทั้งที่ค่าผิด
**ด่านนี้จับการตั้งค่าผิดอย่างซื่อสัตย์ ไม่ได้จับอุปกรณ์ที่โกหก**

> **ฟิลด์ที่ไม่มีใครตรวจก็เหมือนไม่มี** ฟิลด์ `window` อยู่ใน schema
> มาตั้งแต่เวอร์ชันแรกเพื่อป้องกันเรื่องนี้พอดี แต่ไม่มีใครอ่านมัน
> จึงป้องกันอะไรไม่ได้เลย **และยิ่งกว่านั้น มันกลายเป็นที่สะสมของค่าที่ผิด**
> `simulate.py` เคยประกาศ `{fs: 20000, n: 8192}` ทั้งที่ส่ง feature
> ของไฟล์เต็ม 4,883 ms

ผลเต็มใน `experiments/2026-10-09-window-length-mismatch.md`
และ `experiments/2026-10-09-retrain-410ms-window.md`
ตรวจซ้ำด้วย `python src/features/check_window_length.py`

### 4.3 ⚠️ ฟิลด์ `rot_quality` — สำคัญกว่าที่คิด

| ค่า | ความหมาย | ระบบปลายทางต้องทำอะไร |
|---|---|---|
| `ok` | วัดความเร็วรอบได้ปกติ | ใช้ได้ตามปกติ |
| `noisy` | วัดได้แต่สัญญาณแกว่ง | **ประเมินครบทุกตัวชี้วัด** — วัดได้แต่แกว่ง ต่างจาก `lost` ที่วัดไม่ได้เลย |
| `lost` | หาพัลส์ไม่เจอ | **ตอบ `indeterminate` ทันที ห้ามประเมินต่อ** ดูข้างล่าง |
| `stopped` | เครื่องจักรหยุดหมุน | ตอบ `indeterminate` พร้อม caveat `machine_stopped` ไม่ใช่ความผิดปกติ |

สถานะ `stopped` จำเป็นมาก มิฉะนั้นระบบจะแจ้งเตือนทุกครั้งที่ปิดเครื่องตามปกติ

#### 🚨 `lost` ต้องตอบ `indeterminate` ไม่ใช่ "ตัดตัวชี้วัดบางตัวออกแล้วประเมินต่อ"

**เอกสารฉบับนี้เคยเขียนไว้ผิด** ว่าถ้า tachometer เสียก็แค่ตัด `h1_frac` กับ `r21`
ออกแล้วใช้ตัวที่เหลือ **ซึ่งผิด** เพราะเส้นฐานของ**ทุกตัวชี้วัด**เป็นฟังก์ชันของ
`rot_hz` (34 จาก 72 ตัวมีสหสัมพันธ์กับความเร็วรอบเกิน 0.7) ถ้าวัดความเร็วไม่ได้
ค่าที่คาดของทุกตัวไม่มีความหมาย

> **เมื่อ normalize ด้วยตัวแปรใด ความน่าเชื่อถือของตัวแปรนั้นคุมทั้งระบบ**

โค้ดใน `src/service/ingest.py` ทำถูกอยู่แล้วตั้งแต่ด่านที่ 3 ตารางข้างบนคือ
สิ่งที่ล้าหลัง — **เป็นตัวอย่างของกฎข้อ 6 ใน `CLAUDE.md` เป๊ะๆ
คือเอกสารถูกต้องตอนเขียน แล้วโค้ดเดินต่อไปโดยเอกสารไม่ได้ตามไป**

### 4.4 ฟิลด์ `clipped_pct` — สัญญาณล้นสเกล

เปอร์เซ็นต์ของตัวอย่างที่ชนขอบบนหรือขอบล่างของ ADC **ถ้าสัญญาณล้นสเกล
ตัวชี้วัดทุกตัวใช้ไม่ได้** เพราะยอดคลื่นถูกตัดหาย `kurtosis` และ `crest factor`
จะต่ำกว่าความจริงมาก ซึ่งเป็นทิศตรงข้ามกับที่ความเสียหายควรทำ

เกณฑ์ที่เสนอ: ถ้าเกิน 0.1% ให้ตั้ง `rot_quality` เป็นระดับที่ต่ำลงและไม่แจ้งเตือน

`rssi_dbm` จำเป็นเพราะเสาอากาศ WiFi ในตัวของ Raspberry Pi และ ESP32 อ่อนกว่า

### 4.6 ขนาดข้อความ

ตัวชี้วัด 12 ตัว × 6 ช่อง = 72 ค่า บวกส่วนหัวและบริบท
**วัดจากข้อความจริงที่สคริปต์จำลองสร้างได้ 2,254 ไบต์ต่อข้อความ**

> ค่านี้เคยประมาณไว้ที่ 1.8 กิโลไบต์ ซึ่งต่ำไป 25% ตัวเลขในเอกสารนี้ปรับให้ตรงกับ
> ที่วัดได้จริงแล้ว ส่วนที่ทำให้ใหญ่กว่าที่คาดคือชื่อ field แบบ `u_radial.kurt_band`
> ซึ่งยาวกว่าที่ประมาณไว้ ถ้าต้องการลดขนาดจริงจังให้ย่อชื่อช่องเหลือสองตัวอักษร
> จะลดได้ราว 20% แต่จะเสียความชัดเจนในการตามรอยกลับไปยังข้อมูลต้นทาง

เทียบกับสัญญาณดิบที่ 590 กิโลไบต์ต่อวินาทีแล้วคือลดลงราว 2,600 เท่า

### 4.7 ข้อความชนิด `assessment`

เพิ่มเมื่อ 2026-10-04 ตอนทำขั้นที่ 5 ของลำดับการพัฒนา
ผลการทดลองอยู่ใน `experiments/2026-10-04-anomaly-detector.md`

```json
{
  "schema": 1,
  "machine": "motor-03",
  "device_id": "esp32-motor03-a",
  "ts": "2026-10-04T10:30:05.120Z",
  "verdict": "unknown_anomaly",
  "severity": "alarm",
  "score": 14.21,
  "n_exceed": 13,
  "evidence": [
    { "feature": "u_tang.env_floor", "z": 14.21 },
    { "feature": "o_radial.kurt_band", "z": 9.07 }
  ],
  "gate": { "votes": 4, "needed": 4, "window": 5 },
  "context": { "rot_hz": 29.83, "rot_quality": "ok" },
  "model": { "name": "baseline-normal", "rule": "vote", "n_train": 29 },
  "caveats": []
}
```

#### 🚩 `verdict` มีสี่ค่า ไม่ใช่สองค่า

| ค่า | ความหมาย |
|---|---|
| `normal` | อยู่ในขอบเขตของข้อมูลฐาน |
| `unknown_anomaly` | หลุดขอบเขต แต่ยังไม่มีชั้นที่ 2 จึงบอกชนิดไม่ได้ |
| `fault` | หลุดขอบเขต และชั้นที่ 2 จำแนกชนิดได้ — **ยังไม่ได้ทำ** |
| `indeterminate` | **ตัดสินไม่ได้** เช่นเครื่องหยุด หรือความเร็วนอกช่วงข้อมูลฐาน |

**ทำไมต้องมี `unknown_anomaly` แยกจาก `fault`** ออกแบบเดิมมีแค่ปกติกับเสีย
ซึ่งเป็นช่องว่างที่พบตอนทบทวนวรรณกรรม ที่หน้างานจริงจะเกิดกรณี
**ผิดปกติแต่จำแนกชนิดไม่ได้** แน่นอน เพราะเครื่องจักรจริงมีความเสียหายที่
ชุดข้อมูลที่ใช้เทรนไม่มี (เช่น BPFI ซึ่ง MAFAULDA ไม่มีเลย)
ถ้าไม่มีช่องนี้ ระบบจะถูกบังคับให้ตอบว่าเป็นชนิดใดชนิดหนึ่งที่รู้จัก
**อย่างมั่นใจแต่ผิด** ซึ่งแย่กว่าการตอบว่าไม่รู้
แนวทางนี้มาจาก Costa et al. (IEEE Access 2026) ซึ่งใช้ MAFAULDA ชุดเดียวกับเรา
ดู `paper/literature-review.md` ฉบับ 02

**ทำไมต้องมี `indeterminate` แยกจาก `normal`** เพราะ
**"ตรวจแล้วไม่พบความผิดปกติ" กับ "ตรวจไม่ได้" ไม่เหมือนกันเลย**
ถ้ายุบสองอย่างนี้เข้าด้วยกัน ระบบจะรับประกันว่าเครื่องดีทั้งที่ไม่มีใครวัดอยู่
ซึ่งเป็นปัญหาตระกูลเดียวกับที่ Last Will and Testament แก้ในระดับอุปกรณ์ (§3.5)

#### ส่งทุกครั้งที่ประเมิน ไม่ใช่ส่งเฉพาะตอนผิดปกติ

ผู้ที่สมัครรับต้องแยกออกได้ระหว่าง "ประเมินแล้วปกติ" กับ "ไม่มีใครประเมินอยู่"
**ถ้าส่งเฉพาะตอนผิดปกติ ความเงียบจะกำกวม**

#### `evidence` เป็นส่วนที่สำคัญที่สุดของข้อความนี้

ระบบที่บอกได้แค่ "คะแนนความผิดปกติ 0.87" จะไม่มีใครเชื่อถือหน้างาน
ช่างซ่อมต้องรู้ว่าให้ไปดูอะไร `evidence` จึงระบุตัวชี้วัดที่หลุดเกณฑ์พร้อมค่า z
เรียงจากมากไปน้อย ซึ่งต่อกับตารางลายเซ็นใน `CLAUDE.md` หัวข้อ 5 ได้ตรงๆ

#### `severity` กับด่านยืนยันซ้ำ

| ค่า | เมื่อไร |
|---|---|
| `info` | ประเมินแล้วปกติ หรือตัดสินไม่ได้ |
| `warn` | ข้อความนี้ผิดปกติ **แต่ยังไม่ผ่านด่านยืนยันซ้ำ** ยังไม่ปลุกคน |
| `alarm` | ผ่านด่านแล้ว หรือค่าสูงเกินเกณฑ์เตือนทันที |

**ที่คาบส่ง 10 วินาที ระบบได้ 8,640 ข้อความต่อวัน** ถ้าเตือนทันทีทุกข้อความ
ที่ผิดปกติ จะได้การเตือนผิดราว **838 ครั้งต่อวัน** ซึ่งใช้งานไม่ได้
จึงต้องเตือนเมื่อ **5 ใน 6 ข้อความล่าสุด**ผิดปกติ ซึ่งลดลงเหลือราว
**0.41 ครั้งต่อวัน** โดยแลกกับความหน่วง 50 วินาที
อาศัยข้อเท็จจริงว่าความเสียหายจริงอยู่ต่อเนื่องแต่สัญญาณรบกวนไม่อยู่ต่อเนื่อง

(เส้นฐานรุ่นก่อนที่เทรนด้วยไฟล์เต็มใช้ 4 ใน 5 ได้ 534 → 0.60 ครั้งต่อวัน
หน้าต่าง 410 ms ที่สั้นลงมีสัญญาณรบกวนต่อหน้าต่างมากกว่า จึงต้องเพิ่มด่าน
ดู §4.2.1)

## 5. 🚩 การตัดสินใจที่ 3 — คาบการส่งและนโยบายการเก็บข้อมูล

### 5.1 คำนวณปริมาณข้อมูล

ต่อเครื่องจักรหนึ่งเครื่อง เซ็นเซอร์ 6 ช่อง ตัวชี้วัด 12 ตัว

| คาบการส่ง | ข้อความ/วัน | จุดข้อมูล/วัน | MQTT | InfluxDB (ประมาณ) |
|---|---:|---:|---:|---:|
| ทุก 1 วินาที | 86,400 | 6,220,800 | 195 MB/วัน | ~560 MB/เดือน |
| **ทุก 10 วินาที** | **8,640** | **622,080** | **19.5 MB/วัน** | **~56 MB/เดือน** |
| ทุก 60 วินาที | 1,440 | 103,680 | 3.2 MB/วัน | ~9 MB/เดือน |

คอลัมน์ MQTT คิดจากขนาดข้อความจริง 2,254 ไบต์ที่วัดได้ในหัวข้อ 4.6

### 5.2 คาบที่เลือก: **10 วินาที**

**เหตุผล**

- ที่ 1 วินาที ข้อมูล 10 เครื่องจักรกินพื้นที่ **5.6 GB ต่อเดือน** ซึ่งบน microSD
  64 GB ที่ต้องแบ่งให้ระบบปฏิบัติการด้วยนั้นเต็มเร็วเกินไป และเขียนถี่เกินจำเป็น
- ที่ 60 วินาที ช้าเกินกว่าจะจับเหตุการณ์ชั่วคราว เช่นการกระแทกตอนสตาร์ท
- **ความเสื่อมสภาพทางกลเกิดขึ้นในช่วงเวลาเป็นวันถึงสัปดาห์ ไม่ใช่วินาที**
  ความละเอียด 10 วินาทีจึงเพียงพอต่อการติดตามแนวโน้ม

**ปรับคาบอัตโนมัติ** เมื่อตัวชี้วัดตัวใดเกินเกณฑ์ ให้ ESP32 เปลี่ยนเป็นส่งทุก
1 วินาทีเป็นเวลา 5 นาที เพื่อเก็บรายละเอียดของเหตุการณ์ แล้วกลับสู่คาบปกติ

### 5.3 นโยบายการเก็บข้อมูลใน InfluxDB

| bucket | ความละเอียด | เก็บนาน | ขนาดต่อเครื่องจักร | สถานะ |
|---|---|---|---|---|
| `pdm_live` | ตามที่ส่งมา (10 วินาที) | **14 วัน** | ~26 MB | ✅ ใช้งานอยู่ |
| `pdm_hourly` | ย่อเหลือรายชั่วโมง (mean, min, max, count) | **2 ปี** | ~7 MB/ปี | ⬜ ยังไม่ได้ทำ |
| `pdm_events` | การแจ้งเตือนและเหตุการณ์ | **ไม่ลบ** | เล็กมาก | ⬜ ยังไม่ได้ทำ |

**ตอนนี้มี bucket เดียวคือ `pdm_live`** ซึ่งมีสาม measurement คือ `vibration`,
`device_status` และ `assessment` ส่วนการแยก bucket ตามอายุข้อมูลยังไม่ได้ทำ
แปลว่า**ตอนนี้ข้อมูลทุกอย่างหายไปหลัง 14 วัน รวมถึงการแจ้งเตือนด้วย**
ซึ่งยอมรับได้ระหว่างพัฒนา แต่ต้องแก้ก่อนขึ้นระบบจริง

ตามแผนจะใช้ InfluxDB task ย่อข้อมูลจาก `pdm_live` ไป `pdm_hourly` ทุกชั่วโมง

**เหตุผลที่เก็บทั้ง min และ max ไม่ใช่แค่ค่าเฉลี่ย** ค่าเฉลี่ยรายชั่วโมงกลบ
เหตุการณ์กระแทกชั่วคราวจนหายไปหมด ซึ่งเป็นสิ่งที่เราต้องการจับพอดี

### 5.4 นโยบายสำหรับสัญญาณดิบ

สัญญาณดิบ 1 วินาที 6 ช่อง แบบ float32 = **1.2 MB ต่อครั้ง**

| กฎ | ค่า |
|---|---|
| เก็บเมื่อใด | เมื่อพบความผิดปกติ หรือสุ่มเก็บวันละ 1 ครั้งเพื่อใช้เทรนซ้ำ |
| จำนวนสูงสุดต่อวันต่อเครื่องจักร | **10 ครั้ง** (= 12 MB/วัน) |
| เก็บนาน | 30 วัน แล้วลบไฟล์เก่าสุดออก |
| เก็บที่ไหน | **ไฟล์ในระบบไฟล์ ไม่ใช่ใน InfluxDB** |

**ห้ามเก็บสัญญาณดิบลง InfluxDB** เพราะฐานข้อมูลอนุกรมเวลาไม่ได้ออกแบบมารับข้อมูล
ความถี่สูงระดับนี้ จะทำให้ฐานข้อมูลบวมและค้นหาช้าลงทั้งระบบ

### 5.5 การปกป้อง microSD

- ตั้ง `zram` แทน swap บนการ์ด (ทำไปแล้วตอน Checkpoint 1)
- เขียน log ของระบบลง RAM แล้วค่อยเขียนลงการ์ดเป็นช่วง
- เมื่อขึ้นระบบจริงให้ย้ายไปใช้ **NVMe** แทน microSD

## 6. การแปลงข้อความเป็นข้อมูลใน InfluxDB

| ส่วนใน InfluxDB | ที่มาจาก JSON |
|---|---|
| **measurement** | `vibration` |
| **tag** `site` `area` `machine` `sensor` | แยกจาก topic |
| **tag** `device_id` | `device_id` |
| **field** | ทุกค่าใน `features` · ทุกค่าใน `context` · ทุกค่าใน `quality` |
| **time** | `ts` |

### ⚠️ กับดักสำคัญของ InfluxDB: อย่าใส่ค่าที่เปลี่ยนตลอดเป็น tag

InfluxDB สร้างดัชนีให้ tag ทุกตัว จำนวนชุดข้อมูล (series) เท่ากับ**ผลคูณของจำนวน
ค่าที่เป็นไปได้ของทุก tag** ถ้าใส่ `rot_hz` เป็น tag จะได้ series ใหม่ทุกครั้งที่
ความเร็วเปลี่ยนแม้เพียงทศนิยม ทำให้หน่วยความจำเต็มและฐานข้อมูลช้าลงจนใช้ไม่ได้
ปัญหานี้เรียกว่า **high cardinality**

**กฎง่ายๆ: tag ใช้กับค่าที่เป็นชุดจำกัดและเปลี่ยนน้อย ส่วนค่าที่เป็นตัวเลขวัดได้
ให้เป็น field เสมอ**

`rot_quality` เป็น tag ได้เพราะมีเพียง 4 ค่า และใช้กรองบ่อย

## 9. สิ่งที่ยังไม่ตัดสินใจ

รายการนี้เปิดไว้อย่างตรงไปตรงมา จะตัดสินใจเมื่อมีข้อมูลเพียงพอ

- **การยืนยันตัวตนและการเข้ารหัส** ระยะแรกใช้ MQTT ไม่เข้ารหัสในเครือข่ายภายใน
  ก่อนขึ้นระบบจริงต้องเพิ่มชื่อผู้ใช้/รหัสผ่าน และพิจารณา TLS
- **การตั้งเวลาให้ตรงกัน** ESP32 ต้องซิงค์เวลาผ่าน NTP มิฉะนั้น timestamp
  ของแต่ละอุปกรณ์จะเทียบกันไม่ได้ ยังไม่ได้ทดสอบว่าคลาดเคลื่อนแค่ไหนในทางปฏิบัติ
- **ความถี่การสุ่มที่ ESP32 ทำได้จริง** เอกสารนี้สมมติ 20 kHz ซึ่งต่ำกว่าชุดข้อมูล
  MAFAULDA ที่ 51.2 kHz **ต้องวัดของจริงก่อน** เพราะมีผลโดยตรงต่อย่านความถี่สูง
  ที่ใช้ตรวจตลับลูกปืน (ต้องการอย่างน้อย 10 kHz จึงต้องสุ่มอย่างน้อย 20 kHz)
- **เกณฑ์การแจ้งเตือน** ต้องกำหนดจากการกระจายของข้อมูลฐานของเครื่องจักรจริง
  จึงยังตั้งไม่ได้จนกว่าจะเก็บข้อมูลได้
- **จำนวนเครื่องจักรที่ต้องรองรับ** ยังรอสถานประกอบการกำหนด
