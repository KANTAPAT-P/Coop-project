# ออกแบบระบบรับส่งและจัดเก็บข้อมูล (Checkpoint 3)

เอกสารการตัดสินใจก่อนลงมือพัฒนา · 2026-09-27

CLAUDE.md ระบุว่าต้องตัดสินใจ 3 เรื่องก่อนเริ่มสร้างระบบ เอกสารนี้ตัดสินใจทั้งสามเรื่อง
พร้อมเหตุผล **สิ่งเหล่านี้เปลี่ยนยากที่สุดเมื่อข้อมูลเริ่มไหลแล้ว** จึงต้องคิดให้จบก่อน

|---|---|---|
| 1 | โครงสร้าง MQTT topic | §2 |
| 2 | โครงสร้าง JSON ที่ส่ง | §3 |

## 1. หลักการออกแบบ 4 ข้อ

หลักการเหล่านี้มาจากผลการทดลองในช่วงที่ 1 ไม่ใช่จากตำรา

1. **ส่งบริบทการทำงานไปพร้อมตัวชี้วัดเสมอ** — วัดได้แล้วว่าตัวชี้วัดความแรงของช่องหนึ่ง
   กระโดด 4 เท่าเมื่อความเร็วรอบผ่าน 50 Hz โดยที่ความเสียหายไม่ได้เปลี่ยน
   ถ้าไม่มีความเร็วรอบกำกับ ระบบจะแจ้งเตือนผิดทุกครั้งที่มอเตอร์เร่ง
2. **อุปกรณ์ต้องบอกได้ว่าตัวเองไม่มั่นใจ** — พบว่า 7% ของไฟล์ในชุดข้อมูลมีสัญญาณ
   tachometer เสีย ถ้าอุปกรณ์ไม่แจ้งว่าวัดความเร็วไม่ได้ ระบบปลายทางจะใช้ค่าขยะเงียบๆ
3. **ออกแบบเผื่อการเปลี่ยนแปลงตั้งแต่แรก** — ใส่หมายเลขเวอร์ชันของ schema
   และตั้งชื่อ topic ให้เพิ่มเครื่องจักรได้โดยไม่ต้องรื้อ
4. **ปกป้อง microSD** — สาเหตุการตายอันดับหนึ่งของโครงงาน IoT บน Raspberry Pi
   คือการ์ดเสื่อมจากการเขียนซ้ำ ทุกการตัดสินใจเรื่องปริมาณข้อมูลต้องคิดถึงข้อนี้

## 2. 🚩 การตัดสินใจที่ 1 — โครงสร้าง MQTT topic

### 2.1 รูปแบบที่เลือก

```
pdm/<site>/<area>/<machine>/<sensor>/<kind>
```

| ระดับ | ความหมาย | ตัวอย่าง |
|---|---|---|
| `pdm` | คำนำหน้าคงที่ของโครงงานนี้ | `pdm` |
| `<site>` | โรงงานหรือสถานที่ | `plant1` |
| `<area>` | พื้นที่หรือสายการผลิต | `press-line` |
| `<machine>` | เครื่องจักร | `motor-03` |
| `<sensor>` | ชุดเซ็นเซอร์ที่ติดกับเครื่องนั้น | `acc-01` |
| `<kind>` | ชนิดข้อความ | `feature` · `status` · `raw` · `alert` |

**ตัวอย่างจริง**

```
pdm/plant1/press-line/motor-03/acc-01/feature
pdm/plant1/press-line/motor-03/acc-01/status
pdm/plant1/press-line/motor-03/acc-01/raw
pdm/plant1/press-line/motor-03/alert
```

### 2.2 กฎการตั้งชื่อ

- ใช้ได้เฉพาะ **a–z, 0–9 และขีดกลาง** ห้ามเว้นวรรค ห้ามอักษรไทย ห้ามตัวพิมพ์ใหญ่
- ห้ามใช้ `+` และ `#` ในชื่อ เพราะเป็นอักขระ wildcard ของ MQTT
- **ความลึกของ topic ต้องคงที่เสมอ** ถ้าบางเครื่องมี 5 ระดับ บางเครื่องมี 6 ระดับ
  การ subscribe ด้วย wildcard จะได้ผลไม่ตรงกัน เครื่องที่ไม่มีพื้นที่ย่อยให้ใส่ `main`
- **ห้ามใส่ค่าที่เปลี่ยนบ่อยลงใน topic** เช่นความเร็วรอบหรือสถานะ
  ค่าพวกนี้ต้องอยู่ใน payload เท่านั้น มิฉะนั้นจำนวน topic จะระเบิด

### 2.3 รูปแบบการ subscribe ที่ใช้บ่อย

| ต้องการ | topic ที่ subscribe |
|---|---|
| ตัวชี้วัดจากทุกเครื่องจักร | `pdm/+/+/+/+/feature` |
| ทุกอย่างในสายการผลิตหนึ่ง | `pdm/plant1/press-line/#` |
| การแจ้งเตือนทั้งหมด | `pdm/+/+/+/alert` |
| สถานะออนไลน์ของทุกอุปกรณ์ | `pdm/+/+/+/+/status` |

### 2.4 ระดับการรับประกันการส่ง (QoS) และ retained

| ชนิดข้อความ | QoS | retained | เหตุผล |
|---|---|---|---|
| `feature` | **1** | ไม่ | ต้องถึงปลายทางเพื่อไม่ให้กราฟแนวโน้มขาดช่วง แต่ไม่ต้องถึง QoS 2 ที่แพงกว่า ผู้รับกันข้อความซ้ำด้วย timestamp |
| `status` | **1** | **ใช่** | ผู้ subscribe ใหม่ต้องรู้สถานะปัจจุบันทันทีโดยไม่ต้องรอข้อความถัดไป |
| `alert` | **1** | ไม่ | ห้ามหาย |
| `raw` | **1** | ไม่ | ก้อนใหญ่ ส่งเฉพาะตอนจำเป็น |

### 2.5 ⚠️ Last Will and Testament — จุดที่มักถูกมองข้าม

ESP32 ต้องตั้ง **Last Will and Testament (LWT)** ไว้ที่ topic `status` ตอนเชื่อมต่อ
เพื่อให้ broker ประกาศแทนเมื่ออุปกรณ์หลุดการเชื่อมต่อแบบไม่ได้บอกลา

```
topic:    pdm/plant1/press-line/motor-03/acc-01/status
payload:  {"schema":1,"state":"offline","reason":"lwt"}
retained: true
```

**ถ้าไม่ตั้ง LWT ระบบจะแยกไม่ออกระหว่าง "เครื่องจักรปกติ ไม่มีอะไรผิด" กับ
"อุปกรณ์ตายไปแล้ว ไม่มีใครวัดอยู่"** ซึ่งเป็นสองสถานการณ์ที่อันตรายต่างกันสิ้นเชิง

## 3. 🚩 การตัดสินใจที่ 2 — โครงสร้าง JSON

### 3.1 ข้อความชนิด `feature`

```json
{
  "schema": 1,
  "device_id": "esp32-motor03-a",
  "ts": "2026-09-27T10:30:00.000Z",
  "window": { "fs": 20000, "n": 8192 },
  "context": {
    "rot_hz": 29.83,
    "rot_quality": "ok",
    "load_pct": 75,
    "temp_c": 41.2
  },
  "features": {
    "ax.rms": 0.4213, "ax.kurt": 3.102, "ax.crest": 4.85,
    "ax.h1_frac": 0.0891, "ax.r21": 0.158,
    "ay.rms": 0.5102, "ay.kurt": 2.994
  },
  "quality": {
    "clipped_pct": 0.0,
    "tach_jitter_pct": 0.21,
    "uptime_s": 84213
  }
}
```

### 3.2 เหตุผลของแต่ละส่วน

| ฟิลด์ | เหตุผลที่ต้องมี |
|---|---|
| `schema` | หมายเลขเวอร์ชันของโครงสร้าง ทำให้เพิ่มหรือแก้ฟิลด์ภายหลังได้โดยที่ผู้รับเวอร์ชันเก่าไม่พัง |
| `device_id` | ระบุอุปกรณ์ที่ส่ง แยกจาก topic เพราะถ้าย้ายอุปกรณ์ไปเครื่องจักรอื่นจะยังตามรอยได้ |
| `ts` | เวลาตาม **UTC รูปแบบ ISO 8601** ห้ามใช้เวลาท้องถิ่นเพราะจะสับสนตอนเทียบข้ามอุปกรณ์ |
| `window` | ความถี่การสุ่มและจำนวนตัวอย่างที่ใช้คำนวณ **จำเป็นต่อการตีความตัวชี้วัด** ความละเอียดความถี่เท่ากับ `fs/n` ถ้าไม่รู้ค่านี้จะอ่าน `h1_frac` และ `r21` ไม่ได้ |
| `context` | บริบทการทำงาน ดูหลักการข้อ 1 |
| `features` | ตัวชี้วัด ใช้ชื่อแบบ `<ช่อง>.<ตัวชี้วัด>` ให้ตรงกับที่ใช้ในโค้ดวิเคราะห์อยู่แล้ว |
| `quality` | ตัวบอกว่าเชื่อข้อมูลนี้ได้แค่ไหน ดูหลักการข้อ 2 |

### 3.3 ⚠️ ฟิลด์ `rot_quality` — สำคัญกว่าที่คิด

| ค่า | ความหมาย | ระบบปลายทางต้องทำอะไร |
|---|---|---|
| `ok` | วัดความเร็วรอบได้ปกติ | ใช้ได้ตามปกติ |
| `noisy` | วัดได้แต่สัญญาณแกว่ง | ใช้ได้ แต่ลดน้ำหนักของตัวชี้วัดที่อิงความเร็ว (`h1_frac`, `r21`) |
| `lost` | หาพัลส์ไม่เจอ | **ห้ามใช้ตัวชี้วัดที่อิงความเร็วรอบ** และห้ามแจ้งเตือนจากตัวชี้วัดเหล่านั้น |
| `stopped` | เครื่องจักรหยุดหมุน | ข้ามการประเมินทั้งหมด ไม่ใช่ความผิดปกติ |

สถานะ `stopped` จำเป็นมาก มิฉะนั้นระบบจะแจ้งเตือนทุกครั้งที่ปิดเครื่องตามปกติ

### 3.4 ฟิลด์ `clipped_pct` — สัญญาณล้นสเกล

เปอร์เซ็นต์ของตัวอย่างที่ชนขอบบนหรือขอบล่างของ ADC **ถ้าสัญญาณล้นสเกล
ตัวชี้วัดทุกตัวใช้ไม่ได้** เพราะยอดคลื่นถูกตัดหาย `kurtosis` และ `crest factor`
จะต่ำกว่าความจริงมาก ซึ่งเป็นทิศตรงข้ามกับที่ความเสียหายควรทำ

เกณฑ์ที่เสนอ: ถ้าเกิน 0.1% ให้ตั้ง `rot_quality` เป็นระดับที่ต่ำลงและไม่แจ้งเตือน

### 3.5 ข้อความชนิด `status`

ส่งทุก 60 วินาทีเป็น heartbeat และตั้ง retained ไว้

```json
{
  "schema": 1,
  "device_id": "esp32-motor03-a",
  "ts": "2026-09-27T10:30:00.000Z",
  "state": "online",
  "fw": "0.3.1",
  "rssi_dbm": -62,
  "free_heap": 118432
}
```

`rssi_dbm` จำเป็นเพราะเสาอากาศ WiFi ในตัวของ Raspberry Pi และ ESP32 อ่อนกว่า
โทรศัพท์มือถืออย่างเห็นได้ชัด การเฝ้าดูความแรงสัญญาณช่วยวินิจฉัยตอนข้อมูลขาดหาย

### 3.6 ขนาดข้อความ

ตัวชี้วัด 12 ตัว × 6 ช่อง = 72 ค่า บวกส่วนหัวและบริบท ได้ **ราว 1.8 กิโลไบต์ต่อข้อความ**
ซึ่งเทียบกับสัญญาณดิบที่ 590 กิโลไบต์ต่อวินาทีแล้วคือลดลงหลายร้อยเท่า

## 4. 🚩 การตัดสินใจที่ 3 — คาบการส่งและนโยบายการเก็บข้อมูล

### 4.1 คำนวณปริมาณข้อมูล

ต่อเครื่องจักรหนึ่งเครื่อง เซ็นเซอร์ 6 ช่อง ตัวชี้วัด 12 ตัว

| คาบการส่ง | ข้อความ/วัน | จุดข้อมูล/วัน | MQTT | InfluxDB (ประมาณ) |
|---|---:|---:|---:|---:|
| ทุก 1 วินาที | 86,400 | 6,220,800 | 152 MB/วัน | ~560 MB/เดือน |
| **ทุก 10 วินาที** | **8,640** | **622,080** | **15 MB/วัน** | **~56 MB/เดือน** |
| ทุก 60 วินาที | 1,440 | 103,680 | 2.5 MB/วัน | ~9 MB/เดือน |

### 4.2 คาบที่เลือก: **10 วินาที**

**เหตุผล**

- ที่ 1 วินาที ข้อมูล 10 เครื่องจักรกินพื้นที่ **5.6 GB ต่อเดือน** ซึ่งบน microSD
  64 GB ที่ต้องแบ่งให้ระบบปฏิบัติการด้วยนั้นเต็มเร็วเกินไป และเขียนถี่เกินจำเป็น
- ที่ 60 วินาที ช้าเกินกว่าจะจับเหตุการณ์ชั่วคราว เช่นการกระแทกตอนสตาร์ท
- **ความเสื่อมสภาพทางกลเกิดขึ้นในช่วงเวลาเป็นวันถึงสัปดาห์ ไม่ใช่วินาที**
  ความละเอียด 10 วินาทีจึงเพียงพอต่อการติดตามแนวโน้ม

**ปรับคาบอัตโนมัติ** เมื่อตัวชี้วัดตัวใดเกินเกณฑ์ ให้ ESP32 เปลี่ยนเป็นส่งทุก
1 วินาทีเป็นเวลา 5 นาที เพื่อเก็บรายละเอียดของเหตุการณ์ แล้วกลับสู่คาบปกติ

### 4.3 นโยบายการเก็บข้อมูลใน InfluxDB

| bucket | ความละเอียด | เก็บนาน | ขนาดต่อเครื่องจักร |
|---|---|---|---|
| `pdm_live` | ตามที่ส่งมา (10 วินาที) | **14 วัน** | ~26 MB |
| `pdm_hourly` | ย่อเหลือรายชั่วโมง (mean, min, max, count) | **2 ปี** | ~7 MB/ปี |
| `pdm_events` | การแจ้งเตือนและเหตุการณ์ | **ไม่ลบ** | เล็กมาก |

ใช้ InfluxDB task ย่อข้อมูลจาก `pdm_live` ไป `pdm_hourly` ทุกชั่วโมง

**เหตุผลที่เก็บทั้ง min และ max ไม่ใช่แค่ค่าเฉลี่ย** ค่าเฉลี่ยรายชั่วโมงกลบ
เหตุการณ์กระแทกชั่วคราวจนหายไปหมด ซึ่งเป็นสิ่งที่เราต้องการจับพอดี

### 4.4 นโยบายสำหรับสัญญาณดิบ

สัญญาณดิบ 1 วินาที 6 ช่อง แบบ float32 = **1.2 MB ต่อครั้ง**

| กฎ | ค่า |
|---|---|
| เก็บเมื่อใด | เมื่อพบความผิดปกติ หรือสุ่มเก็บวันละ 1 ครั้งเพื่อใช้เทรนซ้ำ |
| จำนวนสูงสุดต่อวันต่อเครื่องจักร | **10 ครั้ง** (= 12 MB/วัน) |
| เก็บนาน | 30 วัน แล้วลบไฟล์เก่าสุดออก |
| เก็บที่ไหน | **ไฟล์ในระบบไฟล์ ไม่ใช่ใน InfluxDB** |

**ห้ามเก็บสัญญาณดิบลง InfluxDB** เพราะฐานข้อมูลอนุกรมเวลาไม่ได้ออกแบบมารับข้อมูล
ความถี่สูงระดับนี้ จะทำให้ฐานข้อมูลบวมและค้นหาช้าลงทั้งระบบ

### 4.5 การปกป้อง microSD

- ตั้ง `zram` แทน swap บนการ์ด (ทำไปแล้วตอน Checkpoint 1)
- เขียน log ของระบบลง RAM แล้วค่อยเขียนลงการ์ดเป็นช่วง
- เมื่อขึ้นระบบจริงให้ย้ายไปใช้ **NVMe** แทน microSD

## 5. การแปลงข้อความเป็นข้อมูลใน InfluxDB

| ส่วนใน InfluxDB | ที่มาจาก JSON |
|---|---|
| **measurement** | `vibration` |
| **tag** `site` `area` `machine` `sensor` | แยกจาก topic |
| **tag** `device_id` | `device_id` |
| **field** | ทุกค่าใน `features` · ทุกค่าใน `context` · ทุกค่าใน `quality` |
| **time** | `ts` |

### ⚠️ กับดักสำคัญของ InfluxDB: อย่าใส่ค่าที่เปลี่ยนตลอดเป็น tag

InfluxDB สร้างดัชนีให้ tag ทุกตัว จำนวนชุดข้อมูล (series) เท่ากับ**ผลคูณของจำนวน
ค่าที่เป็นไปได้ของทุก tag** ถ้าใส่ `rot_hz` เป็น tag จะได้ series ใหม่ทุกครั้งที่
ความเร็วเปลี่ยนแม้เพียงทศนิยม ทำให้หน่วยความจำเต็มและฐานข้อมูลช้าลงจนใช้ไม่ได้
ปัญหานี้เรียกว่า **high cardinality**

## 6. บริการที่ต้องติดตั้ง

| บริการ | อิมเมจ | พอร์ต | หน้าที่ |
|---|---|---|---|
| Mosquitto | `eclipse-mosquitto` | 1883 | MQTT broker |
| InfluxDB | `influxdb:2` | 8086 | ฐานข้อมูลอนุกรมเวลา |
| Grafana | `grafana/grafana` | 3000 | แดชบอร์ดและการแจ้งเตือน |
| Python service | สร้างเอง | — | รับข้อความ ตรวจสอบ เขียนฐานข้อมูล และประเมินแบบจำลอง |

ทั้งหมดกำหนดไว้ใน `stack/docker-compose.yml` ไฟล์เดียว

**พัฒนาบนโน้ตบุ๊กก่อน แล้วจึงย้ายลง Raspberry Pi** เพราะไฟล์ Docker Compose
ชุดเดียวกันรันได้ทั้งสองเครื่อง และการพัฒนาบนโน้ตบุ๊กเร็วกว่ามาก

## 7. ลำดับการพัฒนา

| ขั้น | งาน | ผลที่ได้ |
|---|---|---|
| 1 | เขียน `stack/docker-compose.yml` และไฟล์กำหนดค่าของ Mosquitto | ยกบริการขึ้นได้ครบ |
| 2 | เขียนสคริปต์จำลองการส่งข้อมูล โดยอ่านจากชุดข้อมูล MAFAULDA | มีข้อมูลจริงไหลเข้าระบบโดยยังไม่ต้องมี ESP32 |
| 3 | เขียน Python service รับข้อความและเขียนลง InfluxDB | ข้อมูลเข้าฐานข้อมูล |

| 5 | เพิ่มการประเมินแบบจำลองและการแจ้งเตือน | ระบบครบวงจร |

## 8. สิ่งที่ยังไม่ตัดสินใจ

รายการนี้เปิดไว้อย่างตรงไปตรงมา จะตัดสินใจเมื่อมีข้อมูลเพียงพอ

- **การยืนยันตัวตนและการเข้ารหัส** ระยะแรกใช้ MQTT ไม่เข้ารหัสในเครือข่ายภายใน
  ก่อนขึ้นระบบจริงต้องเพิ่มชื่อผู้ใช้/รหัสผ่าน และพิจารณา TLS
- **การตั้งเวลาให้ตรงกัน** ESP32 ต้องซิงค์เวลาผ่าน NTP มิฉะนั้น timestamp
  ของแต่ละอุปกรณ์จะเทียบกันไม่ได้ ยังไม่ได้ทดสอบว่าคลาดเคลื่อนแค่ไหนในทางปฏิบัติ
- **ความถี่การสุ่มที่ ESP32 ทำได้จริง** เอกสารนี้สมมติ 20 kHz ซึ่งต่ำกว่าชุดข้อมูล
  MAFAULDA ที่ 51.2 kHz **ต้องวัดของจริงก่อน** เพราะมีผลโดยตรงต่อย่านความถี่สูง
  ที่ใช้ตรวจตลับลูกปืน (ต้องการอย่างน้อย 10 kHz จึงต้องสุ่มอย่างน้อย 20 kHz)
- **เกณฑ์การแจ้งเตือน** ต้องกำหนดจากการกระจายของข้อมูลฐานของเครื่องจักรจริง
  จึงยังตั้งไม่ได้จนกว่าจะเก็บข้อมูลได้
- **จำนวนเครื่องจักรที่ต้องรองรับ** ยังรอสถานประกอบการกำหนด
