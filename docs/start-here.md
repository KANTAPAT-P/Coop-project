## 3. ของที่มีอยู่ตอนนี้ แบ่งเป็น 3 กอง

## 4. คำศัพท์ที่เจอบ่อย แปลว่าอะไร

### เกี่ยวกับการวิเคราะห์สัญญาณ

| คำ | แปลง่ายๆ |
|---|---|
| **feature** | ตัวเลขสรุปที่คำนวณจากสัญญาณ เช่น "สั่นแรงแค่ไหน" "สั่นแหลมแค่ไหน" |
| **ลายเซ็น (signature)** | feature ตัวที่บอกได้ว่าเป็นความเสียหายแบบไหน |
| **1× (หนึ่งเท่า)** | ความถี่เท่ากับความเร็วรอบพอดี ถ้าเพลาหมุน 30 รอบต่อวินาที 1× ก็คือ 30 Hz |
| **h1_frac** | พลังงานกี่ % อยู่ที่ 1× → **มากแปลว่าไม่สมดุล** |
| **r21** | พีคที่ 2× สูงกว่าพีคที่ 1× กี่เท่า → **มากแปลว่าเพลาเยื้องศูนย์** |
| **rms** | ความแรงเฉลี่ยของการสั่น |
| **kurtosis** | ความ "แหลม" ของสัญญาณ มีการกระแทกเป็นพัลส์ไหม |
| **envelope** | ดึงจังหวะการกระแทกที่ซ่อนอยู่ในคลื่นความถี่สูงออกมา ใช้กับตลับลูกปืน |
| **tachometer** | เซ็นเซอร์วัดความเร็วรอบ ยิงแสงใส่แถบสะท้อนบนเพลาแล้วนับ |

### เกี่ยวกับ machine learning

| คำ | แปลง่ายๆ |
|---|---|
| **data leakage** | ข้อสอบรั่ว โมเดลเคยเห็นเฉลยมาก่อน เลยได้คะแนนสูงแต่ใช้จริงไม่ได้ |
| **train / test** | ข้อมูลที่ให้โมเดลเรียน / ข้อมูลที่เอาไว้สอบ **ห้ามปนกัน** |
| **supervised** | เรียนจากตัวอย่างที่มีเฉลย |
| **anomaly detection** | เรียนจากของปกติอย่างเดียว แล้วบอกว่าอะไร "ไม่เหมือนปกติ" |
| **Random Forest** | อัลกอริทึมที่เหมือนให้ต้นไม้ตัดสินใจหลายร้อยต้นโหวตกัน |
| **AUC** | คะแนนบอกว่า feature ตัวหนึ่งแยกสองกลุ่มได้ดีแค่ไหน 1.0 = แยกขาด 0.5 = เดาสุ่ม |
| **recall** | ของที่เสียจริง เราจับได้กี่ % |
| **false alarm** | เตือนทั้งที่ไม่มีอะไรผิด |

### เกี่ยวกับระบบ

| คำ | แปลง่ายๆ |
|---|---|
| **MQTT** | วิธีส่งข้อความแบบประหยัดสำหรับอุปกรณ์เล็กๆ |
| **broker** | ตัวกลางที่รับข้อความแล้วส่งต่อ (คือ Mosquitto) |
| **topic** | ที่อยู่ของข้อความ เช่น `pdm/plant1/press-line/motor-03/acc-01/feature` |
| **publish / subscribe** | ส่งข้อความ / สมัครรับข้อความจาก topic นั้น |
| **QoS** | ระดับการรับประกันว่าข้อความจะถึง 0 = ส่งแล้วแล้วกัน · 1 = ถึงอย่างน้อย 1 ครั้ง |
| **LWT** (Last Will) | ข้อความที่ broker ประกาศแทนเราถ้าเราหลุดการเชื่อมต่อกะทันหัน |
| **retained** | ข้อความที่ broker เก็บไว้ ใครมาสมัครทีหลังก็ได้รับทันที |
| **bucket** | ถังเก็บข้อมูลใน InfluxDB เราแบ่งตามอายุของข้อมูล |
| **tag / field** | ใน InfluxDB: tag = ป้ายชื่อที่ใช้กรอง · field = ตัวเลขที่วัดได้ |
| **Docker / container** | วิธีห่อโปรแกรมให้รันเหมือนกันทุกเครื่อง |
| **provisioning** | ตั้งค่าโปรแกรมจากไฟล์แทนการกดในหน้าเว็บ ทำให้ขึ้น git ได้ |

## 5. 6 เรื่องที่ต้องจำ ถ้าจำได้แค่นี้ก็พอ

### 1. เอกสารของชุดข้อมูลเขียนผิด 4 จุด เราจับได้เอง

จุดที่สำคัญที่สุดคือ **ความถี่การสุ่มจริงคือ 51,200 Hz ไม่ใช่ 50,000 Hz** ตามที่เขาเขียน
ถ้าไม่จับได้ การวิเคราะห์ทุกชิ้นจะคลาด 2.4% ไปตลอด

**บทเรียน: อย่าเชื่อเอกสาร ให้ตรวจกับข้อมูลจริงเสมอ**

### 2. ตัวเลขความแม่นยำไม่มีความหมาย ถ้าไม่บอกว่าแบ่งข้อมูลยังไง

เราทดลองแล้วได้ **0.996 / 0.843 / 0.726 จากข้อมูลชุดเดียวกัน โมเดลเดียวกัน
ต่างกันแค่วิธีแบ่ง train/test**

**บทเรียน: แบ่งข้อมูลตามไฟล์หรือตามเงื่อนไขเสมอ ห้ามสุ่ม**

### 3. หาลายเซ็นเจอ 7 จาก 8 แบบ แต่ทฤษฎีอธิบายได้แค่ 2

ที่เหลือคือ "วัดได้ว่าต่างกันจริง แต่ยังไม่รู้ว่าทำไม" ซึ่ง**อาจย้ายไปใช้กับ
เครื่องจักรอื่นไม่ได้**

### 4. ต้องส่งความเร็วรอบไปพร้อมกับตัวเลขเสมอ

เราวัดได้ว่า**ค่าความแรงกระโดด 4 เท่าเมื่อความเร็วข้าม 50 Hz ทั้งที่เครื่องไม่ได้เสียเพิ่ม**
ถ้าไม่ส่งความเร็วไปด้วย ระบบจะเตือนผิดทุกครั้งที่มอเตอร์เร่ง

### 5. QoS 1 ไม่ได้แปลว่าข้อมูลไม่หาย

ทดสอบครั้งแรกส่ง 4,440 ข้อความ **ได้รับแค่ 2,262 หายไปครึ่งหนึ่งโดยไม่มี error ใดๆ**
แก้แล้วด้วยการให้ผู้ส่งหน่วงตัวเองและรอให้คิวระบายก่อนตัดการเชื่อมต่อ

**บทเรียน: ต้องนับจำนวนสองฝั่งเสมอ ไม่งั้นข้อมูลหายแบบไม่รู้ตัว**

### 6. ข้อมูลบนแดชบอร์ดตอนนี้ไม่ใช่ของจริง

สคริปต์จำลองหยิบข้อมูลเดิมมาส่งซ้ำ และ**เส้นกราฟที่ขึ้นลงสวยๆ คือคลื่นไซน์ที่เราเขียนเอง**
ส่วนอุณหภูมิกับโหลดสร้างขึ้นทั้งหมด **ห้ามเอาไปสรุปอะไร**

## 7. ถัดไปทำอะไร

### 7.1 งานวิจัยให้อะไรมาเป็นแนวทาง

อ่าน 12 ฉบับ ทุกฉบับใช้ MAFAULDA ชุดเดียวกับเรา สรุปเต็มใน `paper/literature-review.md`

**ยืนยันของเดิม 6 เรื่อง — ไม่ต้องเปลี่ยนอะไร เอาไปอ้างอิงได้เลย**

| เรื่องที่เราทำไว้ | งานที่หนุน |
|---|---|
| เลือก Random Forest ไม่ใช้ deep learning | **5 ฉบับ** เลือกเหมือนกัน และ Costa วัดได้ว่าไม่ต่างจาก CNN (p = 0.538) |
| `o_tang` / `u_tang` ดีกว่า `u_radial` | Kim ทดลอง 120 รอบได้ tangential 72% > radial 58% |
| ลายเซ็นข้ามฝั่ง (เซ็นเซอร์ฝั่งตรงข้ามจับได้) | Ūselis เจอแบบเดียวกัน F1 100% |
| คลาส normal แยกยากผิดคาด | Ūselis ได้ F1 แค่ 6–38% บนช่อง overhang |
| ต้องแบ่ง train/test ตามไฟล์ | Kim และ Jiang ระบุชัดว่าทำเพื่อ *"avoid leakage"* |
| ส่งความเร็วรอบไปกับ feature ทุกครั้ง | Ali ใช้ความเร็วรอบเป็น feature ตัวแรก |
| หน้าต่างยาว 32,768 แถว | Kim วัดได้ว่ายิ่งยาวยิ่งดีและยังไม่อิ่มตัว |

**ของใหม่ที่ต้องเพิ่ม 4 เรื่อง**

1. 🔥 **order tracking** — ตัดสัญญาณเป็นรอบด้วย tachometer แล้วแปลงจาก "ต่อเวลา"
   เป็น "ต่อมุมเพลา" ทำให้ความถี่ความเสียหายอยู่ตำแหน่งเดิมไม่ว่าความเร็วจะเปลี่ยน
   **นี่คือเรื่องที่อาจารย์ถูกที่สุด** เราแก้ปัญหาความเร็วด้วยการจำกัดช่วง
   ขณะที่วงการมีวิธีมาตรฐานอยู่แล้ว (Sanami, ACC 2026)
   → แต่ `src/data/tachometer.py` ที่ทำไว้คือวัตถุดิบขั้นแรกของเทคนิคนี้พอดี **ไม่เสียเปล่า**
2. **ทางออกที่สาม `unknown`** — ออกแบบของเรามีแค่ "ปกติ" กับ "เสียแบบที่รู้จัก"
   ยังไม่มีช่องสำหรับ "ผิดปกติแต่จำแนกไม่ได้" ซึ่งจะเกิดแน่ที่หน้างาน
   Costa แก้ด้วยการให้โมเดลคืนค่าความมั่นใจ ถ้าต่ำกว่าเกณฑ์ก็ส่งต่อให้ตัวตรวจอีกชั้น
3. **เพิ่ม feature สองตัว** `skewness` และ `spectral entropy` — 3 ฉบับใช้ทั้งคู่
   และคำนวณบน ESP32 ได้
4. **เอา `mic` กลับมา** — เราตัดทิ้งทั้งช่องเพราะเจอกับดักสเกล ซึ่งวัดใหม่แล้ว
   พบว่าเกิดเฉพาะ 25% ของไฟล์ imbalance ไม่ใช่ทั้งคลาส
   แต่กับดักนั้นอยู่แค่ในคลาส imbalance ส่วน Ūselis ได้ `mic` 96% ชนะทุกช่องสั่นสะเทือน
   **ทางที่ถูกคือ normalize ต่อไฟล์ ไม่ใช่ตัดทิ้ง**

**จุดแข็งที่เจอว่าเรานำวรรณกรรม 3 เรื่อง**

- **อัตราการสุ่มจริงคือ 51,200 Hz** — 9 จาก 12 ฉบับใช้ 50 kHz ผิด และไม่มีใครวัดเอง
- **มวลถ่วงปนในคลาส bearing** — 11 จาก 12 ฉบับไม่เอ่ยถึงเลย
- **ตารางลายเซ็นต่อคลาส** — ไม่มีฉบับไหนทำ และไม่มีใครใช้ความถี่ BPFO/BSF/FTF เลย

### 7.2 เหลืออีก 2 ข้อใน Checkpoint 3

recall 0.872 เตือนผิด 1 จาก 47 ไฟล์ปกติ และระบบมีสามชั้นคือ

ทุกข้อความ** เทรนใหม่บนหน้าต่าง 410 ms แล้ว และเพิ่มด่านที่ปฏิเสธข้อความ

**เหลือข้อ 6 ข้อเดียว**

วิธีที่วางไว้คือ **เริ่มจากง่ายที่สุดก่อน** — ดูว่าค่าปกติของเครื่องอยู่ช่วงไหน
